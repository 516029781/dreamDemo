## 2. 必修错误及关闭标准（按执行顺序）

### P0-1 冻结包发生哈希漂移

- **现象**：manifest 中 `delivery/courtyard_scene_demo_sources_v7.zip` 的 SHA-256 为 `f9d9a5d14c11d0836668573457b40fd3842d15ef72c43ca4be08d1bab9e05676`；当前磁盘为 `eaead5b5ae83edcde29fe29d9676c6c58274cce1885118297b3a695fc96cde39`。`source_package_v7.json` 记录的是后一值。现有 n4 manifest 无法准确描述当前载荷。
- **修复**：把 n4 作为已尝试候选保留；从可编辑源派生 `candidate_n5`。先完成修改、构建、采集、自审，再**生成不含最终 manifest 的源 ZIP 并锁定其 SHA**，随后生成引用该源 ZIP 的 manifest。若另做包含 manifest 的最终审阅 ZIP，其自身 SHA 写在包外 `.sha256`，不得让 manifest 引用包含自身的 ZIP，避免循环哈希。归档后校验 manifest 中所有文件 SHA、ZIP 内外同名文件 SHA、重复项、缺失项和 CRC；ZIP 改动后不可只改 manifest 字段“追平”。
- **通过证据**：n5 的 manifest/ZIP/外层哈希清单与磁盘逐项一致，校验命令、退出码、日志、文件数量和散列汇总入包；n4 原包和报告不覆盖。

### P0-2 Q、截图与绑定不是同一构建

- **现象**：`T5/behavior_results_n4.json` 的 build_id 为 `cocos-web-desktop-cocos_build_20261025_235846`；`candidate_n4/bindings/binding_formal_no_ui.json` 的 build_id 为 `cocos-web-desktop-cocos_build_20261026_000915`。旧提交检查报 `Build binding mismatch`。截图绑定本身 verified 不等于整条 Q 链一致。
- **修复**：n5 源和参数冻结后生成唯一正式 build_id。正式无 UI、有 UI、对白、Q01–Q09 行为/画面、binding 从此构建采集；重建一次就让依赖此构建的画面/测量失效，不得混用旧 JSON。运行 `check_bindings.py`、`check_quality.py`、`producer_review.py check` 并保存原输出。
- **通过证据**：manifest、build report、三个正式 binding、Q 结果及最终自审指向同一 build_id 和相符 SHA；完整检查无 pending/fail。

### P0-3 Q02 对照图改变后未重绑

- **现象**：`T5/behavior_results_n4.json` 记录 `T2/reference_comparison.png` SHA 为 `14b8fcdb...`，当前文件为 `39a71cda...`；原 n4 `quality_check_n4.json` 曾给 Q02 pass，稍后的 producer 检查转为 Q02 pending。这证明曾通过的 Q 结果在证据变动后未自动失效。
- **修复**：n5 锁定 P1 截图和当前候选截图后重新生成对照图、Q02 区域观察、Q 结果及其 SHA；任何对照图变化要使 Q02 重新检查。不要仅替换记录中的 SHA 而保留旧观察结论。
- **通过证据**：至少三个明确的 P1/候选对应区域、具体差异、同机位信息；结果中的每个引用文件散列与磁盘相符，Q02 为 pass。

### P1-1 ENV：主体场景仍缺 P1 的纵深和自然细节

- **画面位置**：`T3/formal_no_ui`、`T4/N01_geometry_closeups`、`N02_material_closeups`。主树叶片更细密，但树冠仍像大量叶卡/细枝噪点；最远一层是连续暗色块，少递进的中景；中心及右侧大片规则方砖成为最大视觉面积；花坛、长椅与种植带的精细度和密度不均。n4 自评把 `geometry_craft`、`lighting_contact`、`vegetation_depth` 打 4，报告自身仍记录叶卡、斑驳噪声和稀疏缝隙，4 分理由需要重审。
- **改法**：先改共享 Blender 树/布局母版。树干到枝条逐级收细，叶簇形成大中小团组、疏密空洞与不规则边缘；远景拆为可分辨的前后两层并降低暗块占比；铺地保留可走区但插入有功能的座椅、导视、边缘花坛/落叶和局部磨损，避免均匀撒噪点。石、木、金属分别用近景验证粗糙度、接缝与边缘磨耗。保持角色道路/交互坐标。
- **低成本先验**：固定机位全景 1280×720，树冠/花坛、长椅/材质、远景三处原尺寸或放大近景，与 n4、P1 并排。若轮廓、层次未改善，不启动整套 Cocos 状态采集。
- **关闭标准**：画面不再由重复方砖与单一暗带主导；主树无明显悬浮叶片/等粗分枝；三个材质在游戏视距可区分。逐维根据真实图重评，ENV ≥90 且核心项 ≥3；不得仅把 3 改成 4。

### P1-2 UI：对白遮住主角，纸面语言未统一

- **画面位置**：`T3/dialogue` 和 `T4/N03_ui_before_after`。n4 对白面板高约 176 px（720 高的 24.4%），数字目标已满足，但面板上缘切过主角，角色只露出头部；P1 `t044s` 保留人物完整站姿。n4 的纸面大体可辨，但任务卡、右下操作和对白的边缘/手绘标记不成一个家族；文字层级偏弱，小字可读性需在目标分辨率核验。
- **改法**：先在游戏画布中解决对白期间相机取景、角色位置与 UI 层关系，保证主角完整可见，NPC/交互对象也不被关键文字挡住。再从一个可编辑 UI 母版统一纸边缺口、薄描线、涂鸦笔触、字体粗细和留白；先做对白、任务卡、交互按钮三种代表状态，确认普通/暂停/竖屏安全区后复用到状态矩阵。不要为了通过高度指标继续压缩文字。
- **关闭标准**：对白内容和点击目标清晰，主角站姿完整，文字不溢出/截断；三组 UI 在同一画面读作同一套材料和笔触；UI 逐维重评 ≥90，全部原尺寸状态图可复查。

### P1-3 MIX：角色与环境的细节和光照不同步

- **画面位置**：`T3/formal_ui`、`dialogue`。锁定角色线条清晰，背景仍是平面化石砖与低精度远景；脚底接触影偏贴片，角色像被贴在场景上。对白遮挡进一步破坏主体焦点。n4 自评 `visual_language` 和 `color_light_coherence` 均为 3，MIX 总分只有 80。
- **改法**：待 ENV/UI 母版首轮改善后，以同一相机、同一角色位置重拍无 UI、有 UI、对白。对齐人物脚底接触与地面明暗、树前/树后遮挡、场景局部细节尺度及 UI 明度；优先改共享场景/灯光/构图关系，不用整体滤镜掩盖低模轮廓。
- **关闭标准**：角色不再明显悬浮，主角在三种状态始终是焦点；MIX 每项的两视角证据支持相应 4 分声明，整卡 ≥90。

### P1-4 性能预算与设备证据

- **现象**：n4 Q06 记录 MAP001 约 553 draws、1,552,913 tris；当前预警线分别 400、400,000。预警不是当前自动失败，但新的叶片/阴影方案不能无限加面数。Q09 记录 `device_tested=false`，只证实浏览器适配。
- **改法**：在树/草/远景母版上做实例复用、可视范围裁剪和分级细节；阴影先用局部接触与合理投射体，记录实际 draw/tris、纹理/阴影分辨率和同机位耗时。微信真机性能单独列为未测，不写成已达标。
- **关闭标准**：至少提供 n4→n5 同机位的 draws/tris/帧时间对照和设备条件；性能不能靠删除关键视觉元素“通过”。

## 3. 八小时耗时：有证据的瓶颈与未知项

从 `delivery/performance/` 中以 n4 路径筛选到 **11 次 Blender 定向运行、41 次 Cocos 构建**：Blender 计时合计 2,265.9 秒（37.8 分钟，单次中位 145.5 秒），其中 MAP001 六次约 31.1 分钟；Cocos 合计 1,603.0 秒（26.7 分钟，单次中位 37.6 秒）。逐条来源和计算结果见同目录 `time_audit.json`。两类命令合计约 **64.5 分钟的记录时长**，不是整轮墙钟时长，可能有并行/间隔。n4 文件还显示重复执行 `evidence_regen_n4b/n4c` 和 UI 状态采集，源 ZIP 约 294 MB、465 项；这些阶段没有一致的开始/结束计时。

用户描述的一轮约八小时尚无同范围完整 trace；不能把未记录的约七小时全归因于“模型思考”或“构建”。日志时间跨度也含间隔。即使假设 64.5 分钟全可消除，对八小时的上限影响约 13%，所以**仅提速构建不可能解释或消除一半总耗时**。真正需优先排查的是：大量小改后重复 Cocos 构建、质量未收敛就反复全量采集、自审/打包后证据漂移导致重做，以及缺少编辑/观察/等待阶段日志。

| 优先级 | 瓶颈假设及依据 | 下一轮措施 | 用什么判断有效 |
|---|---|---|---|
| P0 | 无完整阶段 trace，八小时无法归因 | 从领包到交付统一记录编辑、预览、构建、采集、Q、自审、打包、等待；空档标 `unknown` | `events.jsonl` 覆盖整轮，阶段墙钟和总墙钟可核算 |
| P0 | 冻结后又改 ZIP/对照图/构建引用，造成检查失败 | 内容定稿后再生成单一正式 build；manifest 与 ZIP 最后一步冻结，修改即新 candidate | 正式包一次校验通过，哈希漂移 0 |
| P1 | 41 次 Cocos 构建和 6 次 MAP001 生成，说明尝试粒度过细 | 树/材质/UI 先用同机位局部预览并批量合并一组参数改动；仅有可见改善才 Cocos 构建 | 相同质量下构建次数、总构建时长与返修轮数下降 |
| P1 | 全状态证据在 n4b/n4c 重复采集 | 受影响集合决定草稿重采；正式全量采集只在图像与行为局部预检通过后运行一次 | 重采输出数、失效原因和最终覆盖可追溯 |
| P1 | 评分 4 与报告中的可见 gap 并存，低质量仍进入全包 | 固定 P1/n4/n5 同机位联系表，每次改动先写观察结论，重大可见缺陷禁止打包 | 独立复审的重大视觉退回数下降 |
| P2 | n4 高三角面/高 draws，后续加细节可能拖慢采集 | 原生母版共享、实例/LOD/裁剪，预览同时记录成本 | 画质提高时性能预警不恶化；真机状态如实记未测 |

上述是优先级和可验证假设，**不承诺已省 50%**。若要证明 8→4 小时，必须比较同范围、同质量、含返修的两次完整记录；不能只用单次 Blender/Cocos 运行时间推算。

### 下一轮量化目标与计算口径

下面将**实测基线、目标、预期影响**分开。用户所说八小时暂按 480 分钟作为规划参照，尚不是同一候选的连续计时记录；所有节省分钟数均需用 n5 `events.jsonl` 复核。不同措施的时间收益只有在阶段不重叠时才能相加。

| 指标 | n4 已知基线 | n5 目标 | 大致收益或质量变化 | 判断条件 |
|---|---|---|---|---|
| Blender/Cocos 重复运行 | 11/41 次，合计命令计时 64.5 分钟 | 约 4–6/15–20 次，在同等画面和最终覆盖下 | 若单次耗时构成近似，命令时间减少 **50%–65%**，约省 **32–42 分钟**；相当于八小时的 **6.7%–8.8%** | 原始运行次数、各次秒数、输入修改与质量结果均保留；缓存命中不冒充完成 |
| 重复整套证据采集 | n4b/n4c 至少两次完整重采；该阶段缺连续计时 | 视觉/行为局部预检通过后正式全量采集一次 | 整套重采**次数减少约 50%**；可省分钟数暂记未知 | `capture` 阶段起止、输出数、重采原因和最终覆盖完整 |
| 整轮交付时间 | 用户观察约 8 小时，缺完整 trace | 首轮规划 6–7 小时（**缩短约 12.5%–25%**） | 其中构建减少仅解释约 32–42 分钟；另需从重复采集/返工中实测省出约 **20–90 分钟**，否则目标不成立 | 同范围、同质量、相同起止点；分列活跃、等待和 unknown；独立验收退回算入总时间 |
| 更激进的 4 小时目标 | 8 小时观察值 | 4 小时（**缩短 50%**）只作条件目标 | 除构建节省约 32–42 分钟外，还须找到约 **198–208 分钟**可消除的非构建工作；现有日志无法证明 | 先取得完整时间分解，再决定能否实施，不作为 n5 必达承诺 |
| 制作自评与本次看图偏差 | 制作四卡平均 86.25；本次预评平均 76.25，平均绝对差 **10 分** | 平均绝对差 ≤5 分 | **评分校准误差减少至少 50%**，代表更早识别低质，不等于画面质量自动提高 | 下一候选同一冻结画面由制作方和独立审核者逐维评分；本次预评非正式审核，故只作工作基线 |
| 画面质量与 P1 风格目标 | 本次预评 ENV 75、UI 71.25、MIX 65、CHAR 93.75 | 制作侧每卡 ≥90；正式独立 rubric 当前每卡 ≥85 | 要到制作侧 90：ENV **+15 分**、UI **+18.75 分**、MIX **+25 分**；相对当前卡分约 **+20%/+26%/+38%**。这些是 rubric 分数目标，不是像素相似度 | 逐维原图对照、两个相关视角支持 4 分、核心维度底线满足；独立者确认，不能靠改分值 |
| 已知证据链错误 | ZIP 哈希、Q02 图片 SHA、build_id 三类不一致 | 0 类不一致 | 对这三类已知错误实现 **100% 清零** | manifest/ZIP/磁盘全量 SHA 一致；Q01–Q09 和三正式截图同 build_id 且无 pending/fail |
| 时间归因完整度 | 64.5 分钟工具命令有记录；其余阶段缺统一起止 | 整轮墙钟 100% 归入明确阶段或 `unknown`；`unknown` ≤10% | 八小时轮次中无法归因时间目标 ≤48 分钟；这是**测量质量目标**，不能算作节省的时间 | `events.jsonl` 起止无断档，重叠阶段单独列示，summary 能回算墙钟 |

“绘图准确性”在此拆成两件可验事实：**产出质量**看独立 rubric 分数与 P1 锚点缺陷，**模型自判准确性**看自评与独立分差。把两者混成一个“准确率百分比”会掩盖真正的画面问题。n5 达到 90 自评分之前，须先让全景、近景、对白和角色融合的可见缺陷实际关闭。

## 4. 给下一制作模型的执行顺序与日志契约

1. **预检（不做全量生产）**：建 `candidate_n5` 工作区，检查有效合同、90 分政策、`jsonschema` 等校验依赖、n4 保留证据及其实际哈希；登记 N01/N02/N03/MIX 和 P0-1～3 的受影响源与目标截图。角色锁定源复用，47 项已有效原生源不重做。
2. **视觉收敛**：按 ENV 几何/构图 → 材质/光 → UI → MIX。每轮只提交同机位前后图和一行“假设、修改、观察、下一动作”；画面仍不满足本报告关闭标准就回原生母版继续改。三轮无改善要换结构方法，不只调种子/颜色。
3. **行为与性能定向复核**：N09 非出生点暂停/恢复与竖屏返回必须保留，Q02 重新绑定，Q06 成本同机位对照。修改依赖覆盖到的 Q/状态；不受影响的旧源只核 hash，但正式候选的整套 Q 仍要完成。
4. **一次正式冻结**：定稿→唯一正式 build→全部正式截图/Q→绑定→逐维真实自审→源 ZIP 锁定 SHA→引用源 ZIP 的 manifest→可选最终审阅 ZIP 及其包外 SHA→包内外散列核对→`producer_review.py check`。manifest 不得引用包含自身的 ZIP。任一必需文件变动就回到受影响阶段并生成新候选版本，不能在 n5 manifest 上静默补文件。
5. **提交条件**：ENV/CHAR/UI/MIX 各 ≥90，核心维度 ≥3、任意维度 ≥2，Q01–Q09/绑定无 pending/fail，blocking/major 开放项 0，47 组覆盖与原生源可编辑。制作侧检查通过后请求一次集中独立审核；制作模型不自签。

**必须随 n5 提交原始日志**，建议目录 `delivery/next_cycle/n5/performance/`：

- `events.jsonl`：每个阶段开始/结束一条记录，含 `candidate_id, run_id, stage, started_at_utc, ended_at_utc, duration_ms_monotonic, input_sha256, output_sha256, cache_hit, command_or_action, exit_code, status, log_path, defect_id, reason`。阶段包括 `read/plan, edit, local_preview, blender, cocos, capture, Q, visual_review, package, wait/unknown`。人工编辑/观察也写起止；无法归因的间隔写 `unknown`，不假装工具耗时。并行阶段不能相加作墙钟。
- `commands.txt` 和 `logs/`：实际命令、参数、工作目录、stdout/stderr、退出码；有重试就保留每次原始日志，说明重试原因。
- `decisions.jsonl`：每次返修记录缺陷 ID、原图/候选路径、低分维度、所改可编辑源、前后 hash、固定机位观察、采纳/撤销及下一步。评分 4 必须指出两个相关机位/状态的实际改善。
- `summary.json`：整轮墙钟、活跃时间、等待/unknown、各阶段时长与次数、重复构建/重采原因、首次可审时刻、最终缺陷和未测项；与 events 自动汇总并核对。

`events.jsonl` 每行示例（真实执行时替换为实际值，不抄示例当证据）：

```json
{"candidate_id":"candidate_n5","run_id":"n5-env-01","stage":"local_preview","started_at_utc":"2026-10-26T01:00:00Z","ended_at_utc":"2026-10-26T01:02:30Z","duration_ms_monotonic":150000,"input_sha256":"<actual-source-sha>","output_sha256":"<actual-preview-sha>","cache_hit":false,"command_or_action":"fixed-camera tree preview","exit_code":0,"status":"completed","log_path":"delivery/next_cycle/n5/performance/logs/n5-env-01.log","defect_id":"N01","reason":"检查主树轮廓和远景层次"}
```

**交接时不得只写“已优化/继续下一轮”**：附本报告各问题的关闭证据路径、检查器 JSON、原始画面与日志，并明确哪些仍 pending。日志旨在下轮识别 8 小时真实瓶颈，不是让模型每个小动作另写长文。
