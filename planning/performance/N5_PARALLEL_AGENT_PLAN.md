# n5 子代理并行制作与单点集成方案

更新：2026-10-26。适用当前 `candidate_n5` 美术返修；本文件是排程方案，**未证明提速**。有效范围、评分和放行仍以当前工作包、`art_review/rubric.json`、`planning/execution/producer_review_policy.json` 为准。执行细节见 `N5_EXECUTION_DESIGN_AND_GAP_AUDIT.md` 与 `knowledge/N5_VISUAL_PRODUCTION_PLAYBOOK.md`。

## 1. 并行的边界

可同时做的是**输入独立、输出隔离的源制作或工具准备**。`demo_n5` 的最终场景、Cocos 构建、Q/截图绑定、制作侧总评分、源 ZIP/manifest 由**一个集成人**依次执行。子代理可对自己的局部成果做批判性自审，但不能给完整候选自签独立审核。

当前仓库含大量未提交的 n3/n4 源与证据。直接从 Git HEAD 新建 worktree，可能拿不到这些输入。并行启动前，集成人先建立 `candidate_n5` 的**明确基线**：列出要继承的 n4 可编辑源、路径及 SHA，复制到 n5 的候选工作区；n2/n4 原件只读。待基线进入可复现的 Git 提交或版本化快照后，才可改用独立 worktree。没有快照时，使用同一工作区中**互不重叠的 n5 路径**，严格指定文件所有者；不让多个代理碰 `demo_n5/assets/scripts/CourtyardBootstrap.ts` 或同一 Blender 场景文件。

资源也要隔离：每个代理用独立 `run_id`、输出目录和日志路径。共享机器上大型 Blender 构建与 Cocos 构建进入集成人队列，避免同时争 GPU/内存、覆盖默认日志或占同一端口。独立 SVG/脚本检查可同时运行。

## 2. 推荐依赖图与并行批次

```text
基线快照 + 文件所有权 + 三图诊断 + 相机灰盒选择（集成人）
      ├─ 工具代理：T0/T1 ── T3 定向采集 ── T4 冻结预检
      ├─ 环境代理：树 A/B/C ── 远景/铺地草稿 ── 材质试件
      └─ UI 代理：纸面/字体样板 ── 三组件状态样板

T0/T1 + 树局部试件有效 + 正式镜头已选
      └─ 集成人立即做第一次 MAP001/Cocos 三图
         （不等待 UI 样板、T3/T4 或远景/材质全部完成）

各源局部有效 ── 集成人逐项合入并定向复拍 ── MIX 收敛
      └─ 唯一正式 build → 全量 Q/47 组/截图 → 自审 → 冻结
```

这是**就绪即推进**，不是必须等一整波所有代理结束。树、远景、UI 可以并行做源与局部预览，但最终 MAP001/Cocos 表现由集成人判定。首个 MAP001 仅依赖相机、n5 工具入口与树试件；UI 源未完成时先保留基线 UI，并明确该次截图不是最终 UI 证据。工具代理完成 T0/T1 后立即做 T3/T4，不能等首次 MAP001 完成才着手。远景/铺地有固定镜头和文件所有权后即可做独立草稿，最终合入时再核树的遮挡与整图关系。材质母版可先以固定光试件制作，正式灯光留给集成人。若相机尚未决定，树/UI 只做不依赖镜头的原生样板；游戏视距对照等镜头定稿。UI 纸面 SVG 与对白相机脚本分开：前者可并行，后者属于最终场景集成。

### 第一波：集成人 + 最多三个子代理

| 负责者 | 独占输入/可改路径 | 交付物与局部门 | 不碰的文件/动作 |
|---|---|---|---|
| 集成人 | n5 基线清单、相机灰盒、`demo_n5` 场景与总日志 | n4 三正式图问题排序；A/B 镜头、Q01/交互/遮挡代价；冻结共享参数与目录约定 | 不抢改子代理的树/UI/工具源；不在源未定时生成正式 manifest |
| 子代理 T（工具） | n5 参数化入口、日志封装、定向采集与冻结预检；指定 `tools/` 与 `delivery/next_cycle/n5/` 的工具文件 | 先 T0/T1：显式 candidate/run/build report、唯一日志及双 run_id 负例；随后立即 T3/T4，不等首次 MAP001 | 不改 n4 冻结源、不改美术、rubric、总账本或正式候选状态 |
| 子代理 E（树） | `tools/blender_n5/build_env_courtyard.py` 及自己独占的树试件目录 | A/B/C 同种子消融、枝线/剪影/游戏视距预览、叶簇/tri 数、源 diff 与 SHA | 不改 `build_map001.py`、Cocos 场景、全局相机或自评分 |
| 子代理 U（UI 美术） | `tools/ui_n5/` 与 n5 SVG/字体母版；局部组件预览目录 | 对白/任务卡/按钮三组件纸面样板、1280×720 原尺寸排版、触控/文字边界说明 | 不改 `CourtyardBootstrap.ts` 的对白状态/相机；不声称游戏 canvas 已通过 |

子代理 T 的参数化接口先由集成人给出字段契约；若接口尚未就绪，E/U 可在隔离试件目录做原生预览，不能写入最终 `demo_n5` 或复用 n4 的构建 ID。T 完成后，集成人核其双 run_id 负例，再接入其他源。

### 后续就绪任务：不用等整波完成

| 任务 | 可并行条件 | 独占源 | 集成前必须给出的结果 |
|---|---|---|---|
| 远景与铺地 | 正式镜头已选、文件所有者空闲；可用基线树做草稿，不必等树最终合入 | `tools/blender_n5/build_map001.py`、`env001_stone_paving.py` | 远景逐层开关试件、路面/通路图、同机位灰阶、tri/材质槽变化；正式合入再核树遮挡，不得挡碰撞与互动 |
| 三材质母版 | 固定光/UV 尺度已约定、代理有空位；不必等第一次 Cocos 三图 | `tools/textures_n5/`、材料母版源 | base/normal/PBR 对照、UV/色彩空间说明、纹理尺寸与材质槽；正式灯光留给集成人 |
| 定向采集与冻结工具 | T0/T1 接口已通过，工具代理立即接续 | n5 采集脚本与 n5 打包/预检脚本，前后顺序由工具代理负责 | T3 定向/全量两模式、T4 SHA/CRC/缺失/重复负例；不能用 n4 截图当 n5 通过证据 |

这里的“通过”由制作侧按源图、命令和局部检查自行判定，不是等待外部评审者回复。未通过时，原代理根据具体失败图继续返修；已完成的代理立即接续不依赖失败项的任务。最多三个子代理席位时，按当前关键路径把完成 E/U/T 的代理转给就绪任务；无需把代理数量等同于任务数量。若 `build_map001.py` 的远景和铺地都要改，交同一代理或先后交接，避免同文件并行编辑。

## 3. 单一集成门：防止并行变成返工

每个子代理只交**源级候选**，并附：`run_id`、基线 SHA、改动文件清单、可重跑命令及原始日志、同参数前后图、预期与实际差别、发现的反例、tri/draw/纹理成本、已测/未测、接口或依赖变化。不能只说“已完成/达到 90”。集成人先核路径不冲突、SHA 对应、可重跑，再把成果合到 n5；有冲突退回对应所有者，不靠最后写入者覆盖。

集成顺序：① 基线、镜头、T0/T1；② 树试件有效就做首次 MAP001/Cocos 三图；③ 远景/铺地、材质、UI 原生资产哪个就绪就先合哪个，按受影响范围定向复拍；④ Cocos 的全局灯光、对白行为与角色接地统一处理 MIX；⑤ 三正式图局部质量判断；⑥ 唯一正式 build 的全部状态/Q/47 组、评分、源 ZIP→manifest→包外 SHA。T3/T4 与②–④并行准备，须在⑥开始前通过。每步只让集成人写共享 `demo_n5` 与正式输出。源或构建更改后，按依赖重采受影响证据；最终完整检查仍一次性从同一 build 执行。

视觉反馈由集成人集中判读：子代理 E 的树剪影好，不代表全景 ENV 好；U 的 SVG 好，不代表 UI 遮挡或 MIX 好；材质近景好，不代表游戏视距有区别。若整图没有预期改善，附截图和具体失分维度退回该源所有者继续修；三次无改善切换构造机制。子代理之间不相互修改对方源，也不在未合并的各自分支上做最终评分。

## 4. 哪些步骤必须串行

| 步骤 | 串行原因 |
|---|---|
| 正式相机选择与交互/Q01/Q03 判断 | 它决定所有游戏视距预览；后改会让布局/UI/截图比较失效 |
| 同一树或 MAP001 主文件的多种变体合并 | 同一可编辑源与导出资产，最后写入会覆盖另一人的参数 |
| Cocos 全局灯光、对白相机、接触影、角色遮挡整合 | 共同决定 ENV/UI/MIX，同改 `CourtyardBootstrap.ts` 容易相互覆盖；必须在一份真画布里看 |
| 单机大型 Blender/Cocos 生产构建 | 共享 GPU、内存、端口和默认输出；可排队，不能把并发数当吞吐率 |
| 正式 build、Q/三正式图/绑定、评分、源 ZIP/manifest | 需要同一确定输入和 build_id；任何中途改动会使证据失效 |
| 独立验收 | 必须基于已冻结的完整候选；制作子代理的互评不等于独立放行 |

## 5. 连续执行与停止条件

当前工作包显示 `I07 ready=True`、未完成制作前序为零，P08/V08/V09/I08/I09 是**最终评审或放行依赖**，不阻塞 n5 美术制作。集成人开始后持续推进到 I07 的完整制作侧候选：47 组覆盖、正式画面与行为/Q/绑定同源、四卡真实自评各 ≥90、开放严重问题为零、源 ZIP/manifest 校验通过。此时一次性交付集中独立审核；未获独立结论时标为 `producer_complete_pending_review`，不写正式放行。

以下情况**不能成为制作中途停工理由**：某子代理局部检查没过、ENV/UI/MIX 自评低分、`producer_review.py` 返回 `producer_rework_required`、Q/哈希/绑定失败、构建脚本缺少 n5 参数、已达到试点构建次数、P08/V09 尚未审核。对应动作是修源、改制作方法、补工具或重采受影响证据，并继续其他独立工作；连续三次无改善则换机制，不结束执行轮。子代理迟滞或交付不可复现时，集成人收回该文件所有权继续处理或重分配，不能一直等回信。

只有当前制作范围已经完整并通过制作侧筛选，或确有外部资源/权限缺失且所有独立工作都无法推进，或用户明确暂停，或会话/运行限制要求交接时，才结束制作轮。例外结束时保存真实检查点：现有源和 SHA、最后成功的 build/capture、失败图与命令、下一项可执行修改、未完成的任务；不能把“等独立审核”写成半成品的阻塞原因。当前范围是 `art_required` 的 I07 **完整美术候选**；游戏玩法与微信发布属于后续 `game_deferred`，本轮不自动宣称整个游戏完成。

## 6. 衡量并行是否真的更快

在 `performance/events.jsonl` 给每个事件加 `agent_id`、`work_package_id`、`depends_on_run_ids`、`resource_lock`（如 `blender`, `cocos`, `none`）、`merge_wait_ms` 和 `rework_cause`。单代理时长不能相加当总工期；从共同起点到制作侧可审候选的**墙钟**，按事件区间并集计算。记录：集成等待、文件冲突、因上游相机/源变化重做的截图、合并后返修轮数和最终四卡质量。

**可估算的只有条件情景，尚没有 n4 独立源制作阶段的持续计时。**设可独立且未被构建次数优化消除的制作时间总量为 `P`，三个子代理各自占用时间为 `p1,p2,p3`，额外协调/合并/返修时间为 `H`，则理想的净节省约为 `P - max(p1,p2,p3) - H`；若任务不均衡或集成必须提前等待关键代理，节省会更小，甚至为负。以下仅以用户观察的一轮 480 分钟为规划参照，不是实测预测：

| 情景假设（非实测） | P：可并行源制作 | 三代理最长路径（假设均分） | H：新增协调返修 | 净省时 | 480 分钟参照下 |
|---|---:|---:|---:|---:|---:|
| 保守 | 60 分钟 | 20 分钟 | 15 分钟 | 25 分钟（约 5%） | 约 7 小时 35 分 |
| 中间 | 120 分钟 | 40 分钟 | 30 分钟 | 50 分钟（约 10%） | 约 7 小时 10 分 |
| 有利 | 180 分钟 | 60 分钟 | 45 分钟 | 75 分钟（约 16%） | 约 6 小时 45 分 |

这张表**不是“n5 必能节省 25–75 分钟”**：`P/H` 目前都缺追踪数据。已记录的 n4 Blender+Cocos 共约 64.5 分钟只是命令时间，且大型构建仍需排队；它不能证明源制作有 60/120/180 分钟可并行。既有 n5 运行次数优化另有约 32–42 分钟的条件估算；只有 n5 日志证实两类收益作用于不重叠区间且画质门槛相同，才能合并计算。两者都顺利的中间情景约从 8 小时降到 6 小时 28–38 分，属于**待验证计算**。要压到 4 小时，在这个中间情景之外还需额外找到约 148–158 分钟的真实可消除关键路径工作，现有证据不足。

第一波完成时立即评估并行成本并调整第二波排程，**不中断 I07 制作**。只有在**相同范围、同一质量门槛**下，墙钟缩短且合并返工与证据错配没有增加，才把该并行方式保留到后续候选。n4 的 Blender/Cocos 命令累计约 64.5 分钟，不能据此承诺并行把用户观察的八小时减半；主要潜在收益是原生源制作与工具开发重叠，最终构建和审核仍在关键路径上。若共享机器构建相互拖慢、集成人等待接口或跨代理返修增多，减少并行槽位或重新切分文件所有权。
