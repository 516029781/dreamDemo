版本：实施方案 1.1（2026-10-25）。不修改 `PROJECT_TASKS.json`、生效合同、rubric 或独立审核结论。当前模式仍为 `candidate_first_final_review`。最新冻结候选 `candidate_n2` 已由独立审核退回，详见 `art_review/reports/independent_20261025_candidate_n2/REPORT.md`；本轮可执行规范见同目录 `REWORK_EXECUTION_SPEC.md`。其源、构建、相机、UI 与证据保持只读；返修生成新候选。

## 0. 本轮事实与优先改造点

`candidate_n2` 的源/构建/manifest/ZIP 哈希一致，N04/N05/N07/N08 有效改善；制作侧四卡为 70/93.75/75/75，独立为 62.5/93.75/65/58.75。首次独立运行发现 N09：移动后暂停再恢复会回到出生点；旧 Q04 在出生点测恢复，漏掉此事。由此可见，当前最大返工源是**视觉母版未在昂贵的全包冻结前收敛**，其次是行为用例未从非默认状态进入。完整耗时基线仍缺，不宣称已经提速 50%。

本轮实施顺序是：锁定缺陷和同机位参照 → 低成本场景/组件预览 → 非默认状态行为回归 → 受影响构建与采集 → 制作侧逐维看图与打分 → 一次完整冻结/打包 → 集中独立审核。每一步只复用哈希未变且依赖未受影响的证据。批量任务已完成，不重跑 47 项制作；核最终覆盖即可。

n3 的 Q/绑定通过，制作侧 ENV/CHAR/UI/MIX 为 75/93.75/75/75，检查器明确返回 `producer_rework_required`。制作方记录了开放差距和 n4 下一动作，但本轮报告停在“未达标、未提交”；流程工具还把检查状态显示为 `not_due_until_full_candidate`，入口文字写死 n3。修正为：工作包读取最近一次尝试的真实筛选状态，候选 ID 读活动返修指针；低分后必须做至少一次对应原生源修改和同机位预览，再更新检查点。当前制作侧提交筛选线为90；独立验收门槛不变，也不靠提分声明代替图像改善。

## 1. 对现有方案的复核

现有工作包、定向构建、同候选采集和最终集中审核方向合理，应该保留。真正的缺口在质量决策和证据生命周期：

1. **样板“通过”的含义不清**：V07 是制作侧预检，可以支持扩批，但不能表示独立视觉批准。必须明确扩批承担的返工风险及共享母版变更的回流范围。
2. **评分能算对，却未必看对**：`producer_review.py` 可核字段、权重、哈希和Q结果，不能从图片判断 P1 风格。上次全量评分复制样张卡片、47项统一pass，仍产生了制作侧四卡约90分与独立 ENV52.5/UI65/MIX58.75 的差距。
3. **测试可被脚本“演示通过”**：Q01测的是投影代理，Q09脚本主动设置旋转提示；须区分真实用户事件、应用响应和测试注入状态。
4. **冻结证据会漂移**：最终审阅ZIP里两份元数据已落后磁盘；提交清单、构建、采集、评分和审阅包需要一致的候选ID与失效规则。
5. **优化缺端到端计量**：有命令计时和局部构建能力，但没有从领取工作包到首次独立审核通过的完整耗时/返修次数记录。不得仅凭任务数或单次构建时间声称提速。

因此，上一版“样板—批量—自动验证—自审—集中审核”作为骨架成立，但不能直接当实施规范。以下补齐状态、契约、证据、返修与衡量方法。

## 2. 统一状态与责任

每个交付对象（资产、UI组件、行为、地图集成、整包）使用同一状态语义；现有任务ID和 `PROJECT_TASKS.json` 仍是唯一任务状态，下面是产物质量状态，不再另建任务账本。

| 状态 | 含义 | 可执行下一步 |
|---|---|---|
| `draft` | 可编辑源或运行草稿已产出，质量未验证 | 局部制作与预览 |
| `technically_verified` | 源、构建、真实事件/画布、依赖和文件完整性检查通过 | 视觉自审 |
| `producer_visual_ready` | 制作侧对照P1逐维审看，达到本阶段自审门槛且无未解决严重问题 | 同母版批量制作或完整候选提交 |
| `candidate_frozen` | 同一候选ID下源→导出→构建→采集→评分→manifest一致 | 最终集中独立审核 |
| `independent_rework` | 独立审核提出具体缺陷 | 只返修影响对象与依赖产物，重建新候选 |
| `independently_approved` | 独立审核与现有合同/证书链实际通过 | 对应范围正式放行 |

制作模型可以写前三个质量状态并冻结候选；不能给自己写 `independently_approved`。`producer_visual_ready` 只是扩批风险控制，不增加P08/V09中途签字。完整候选未达制作侧门槛时继续返修，不因账本没有新的ready任务而停工。

## 3. 工作包输入与输出契约

每包只需一份简短、机器可读的“工作卡”，从现有任务、合同和源文件生成索引，不手抄第二份事实源。建议字段：

```json
{
  "package_id": "B07",
  "task_ids": ["A-UI001"],
  "candidate_id": "cycle_03_draft_02",
  "goal": "在全部UI状态复用同一纸片与涂鸦组件规范",
  "reference_features": ["P1 U01", "P1 U02"],
  "inputs": [{"path": "...", "sha256": "..."}],
  "expected_outputs": ["native_source", "engine_canvas", "state_matrix"],
  "acceptance": ["真实状态覆盖", "逐维视觉观察", "可编辑源可重开"],
  "affected_outputs": [],
  "open_defects": [],
  "resume_action": "..."
}
```

字段中 `goal` 写效果，`acceptance` 写如何观察效果。资产文件存在、命令退出0和制作任务done分别只证明对应事实。每包交付一条可复现命令记录、当前产物索引、前后画面、缺陷闭合或未解说明。包内多个任务可以共享构建/采集，但每个任务仍有自己的实际完成证据。

## 4. 从参考特征到批量制作

### 4.1 建立可复用的视觉标准，而非单图打分

基于现有P1原帧和rubric，制作一页“风格锚点表”：每个锚点记录参考原帧区域、可见特征、反例、允许变化和候选图区域。至少覆盖环境层次/树叶尺度/材质与光影、角色比例与线色、UI纸片/图标/排版、角色与场景融合。描述可观察的形状、颜色、透明度、密度和关系；不要求逐像素复制P1，也不把文件数量当风格质量。

每类共享系统先做**能在实际Cocos画布显示的代表样板**：环境+角色同屏、一个完整UI组件族、一个含正常/暂停/对白的状态链。样板自审低分可继续制作与修复；达到V07制作侧门槛后可以扩批，但仍标 `candidate_not_independently_approved`。批量过程若改变母版、相机、灯光、字体或共享组件，样板及相关资产自动回到需复核状态。

### 4.2 批量生产的单位是母版/组件

47项仍逐项有源、用途、引擎画面和检查记录；制作操作按植被、材质、道具、角色、UI组件、FX等共享系统集中。每项先分为“有效复用 / 局部修改 / 结构返修 / 缺失新增”。有效复用项只做当前候选适配与核验，不为凑任务数重新生成。AI Image/扩散生图仍按现有AGENTS禁用；保留Blender、SVG/Krita原生图层、锁定Spine等可编辑链路。

## 5. 证据与验证分层

| 层 | 检查内容 | 失败时处理 |
|---|---|---|
| A 文件链 | 原生源可开、导出/构建/采集同候选ID和hash、manifest/ZIP一致 | 失效产物重做；不进入画质评分 |
| B 真实运行 | 在干净页面由键盘/触控/resize等真实事件驱动；采实际canvas和运行状态 | 修代码或采集方法；不得在测试脚本直接设置目标结果 |
| C 视觉证据 | 固定机位原尺寸图 + P1对应区域；必要局部放大、状态前后图 | 逐维指出缺口，修改母版/布局/材质再重采 |
| D 制作侧判定 | ENV/CHAR/UI/MIX逐维打分、具体观察、缺陷/修复、47项逐项差异 | 未达门槛自己修；机械checker仅核结构与一致性 |
| E 独立判定 | 完整候选后对同一冻结ID集中复审、缺陷回流、证书链 | `independent_rework` 或正式放行 |

每项行为检查必须有**正向对照、进入非默认状态、刺激、观察、反向/恢复对照**。例如 Q04：键盘和触控分别先离开出生点至少可测量的距离，记录恢复前世界坐标，暂停期间无位移，恢复后无新输入时位置/任务/相机不变，新输入后能移动；横屏→竖屏→横屏也从非出生点进入。方向适配不能调用UI状态setter。状态检查至少覆盖默认、已移动/已操作、返回三种状态，避免同值断言。实际像素问题必须测渲染结果，投影/配置值只能作诊断。

自审报告里的高分要绑定至少两个相关机位或状态，并写可见理由。检查器可以标出重复理由、同分批量填充、证据静态/不变、P1对照缺失和候选哈希不一致；这些是**需要重审的信号**，不由算法自动判定画面好坏。不能仅通过改阈值、模板措辞或rubric取得通过。

## 6. 候选版本与失效传播

统一 `candidate_id` 绑定原生源、参数、导出、Cocos构建、采集、Q结果、自审、manifest和审阅ZIP。草稿可只重做影响集合；正式冻结要完整校验。建议最小失效规则：

- 资产局部几何/纹理变化：该源、导出、使用它的场景与对应机位/资产预览失效。
- 共享材质、光照或相机变化：所有消费该参数的场景画面、视觉评分与相关测量失效。
- UI母版、字体或布局变化：使用该组件的状态矩阵及相关触控/安全区检查失效。
- 输入、角色RT或状态逻辑变化：对应真实行为、动画、遮挡和相关画面失效。
- 合同/rubric/采集器变化：明确记录规则版本与影响范围；必要时重新评分/采集，不继承旧批准。

失效按源文件和参数内容hash及依赖关系判断，mtime只用于发现候选变化。不能拿旧截图配新build。先锁定所有源、截图、Q 和评分，再生成源 ZIP 并记录 SHA，随后生成引用它的 manifest；若另做包含 manifest 的审阅 ZIP，其自身 SHA 写在包外，避免循环引用。核对包内外后冻结候选；任何后续修改都产生新候选版本。保持历史包只读，报告可追溯到确切版本。

## 7. 返修与最终审核循环

独立审核每个问题输出：缺陷ID、严重度、观察到的画面/行为、证据、受影响对象、建议动作、关闭标准。制作侧将缺陷映射到共享原因和任务，而不是按截图逐个修补；修改后重新计算影响集合。本轮 N01/N02/N03 是共享视觉系统，N09 是非默认状态恢复行为；N04/N05/N07/N08 的已有有效证据保留，但任何相关源/构建变化仍须按失效图复核。返修工作卡不能只写“优化风格”，必须标出可编辑母版、固定机位、对照图、应达到的 rubric 维度和失败时下一种方法。

连续三轮同一问题无可观察改善：暂停该问题的参数微调，记录已排除假设，检查建模/构图/渲染机制；其他独立可做工作继续。不设置自动“到时停止”或中途独立签字。达到完整提交条件后才做一次集中审核；若独立审核退回，只针对真实受影响集合返修并形成新候选。

## 8. 实施顺序与验收

| 顺序 | 改造 | 产物 | 完成判据 |
|---|---|---|---|
| 0 | 保留 n2 冻结基线，登记独立 N01/N02/N03/N09 | 固定哈希、开放缺陷与受影响清单 | 可追溯 n2，不覆盖其源/证据 |

| 2 | Q04 增补非出生点与返回状态，先做针对性运行 | 键盘/触控/竖屏恢复坐标与画面记录 | 位置、任务和相机连续，暂停期间零位移 |
| 3 | 依赖失效清单与增量构建 | dirty 源/导出/场景/截图/Q 列表 | 只重跑受影响对象；最终完整检查仍执行 |
| 4 | 制作侧逐维自审和检查器筛选 | 四卡、P1 对照、缺陷闭合、47项覆盖 | 四卡各≥90、核心≥3、任维≥2、Q/绑定通过、严重问题0；不虚填高分；独立验收rubric不变 |

先在 **n2→新候选的 N01/N02/N03/N09 返修**上试点，不先开发新平台；工具只做消除实际重复劳动和漏检的最小改动。每个阶段记开始/结束、人工等待与重做原因；先得到可比基线，再讨论 50% 时间目标。实施涉及合同/rubric或P任务时按现有版本化权限执行；本方案不授予制作模型修改审核结果的权限。

## 9. 衡量是否真的更快、更可靠

主要指标：同范围从领取到**首次独立审核通过**的日历时间与制作侧活跃墙钟时间，二者分开报。辅助指标：制作/构建/渲染/采集/验证/打包时间、工具首次开发成本、返修轮数、独立审核发现的严重漏检数、旧证据误用数、共享原因一次修改覆盖的资产数。当前无完整旧基线时，只报告新一轮实测值和不可比原因，不宣称已减少50%。

质量护栏：47项覆盖、可编辑源、P1对照、真实行为、最终完整采集及独立放行标准保持不变。优化成功必须表现为**相同范围、更少返修或更少无关重跑，且独立审核质量不下降**；任务数增长、脚本退出0或制作侧90分本身都不是成功指标。

## 10. n4 后的实际修订（2026-10-26）

用户恢复制作侧逐卡 90 分筛选线。n4 复测、错误关闭标准、执行日志与下一轮优先级详见 `art_review/reports/candidate_n4_provisional_20261026/REPORT.md`，该报告是本方案在 n4→n5 的执行补充。n4 的制作自评分 87.5/93.75/83.75/80，源 ZIP 哈希漂移、Q02 对照图 SHA 失效、Q 结果和正式截图的 build_id 不同，故整包不能因局部质量检查曾 pass 就进入最终审核。

n5 的逐类变更运行决策、T0–T4 最小工具缺口和其他量化目标的执行/验收，使用 `planning/performance/N5_EXECUTION_DESIGN_AND_GAP_AUDIT.md`。前述 4–6/15–20 次是**条件试点预算**；现有工具仍需候选参数化、唯一日志路径和显式 build report，不能作为已实现能力交接。

制作侧自我学习闭环使用 `planning/execution/SELF_LEARNING_LOOP.md`：相关经验检索、编辑前假设、实际预览后的反例搜索、失败归因与返修、批次总结、经验提案及复验。`planning/execution/LESSONS.md` 只收有触发条件和证据路径的短规则；未验证规则不得改变合同/评分，也不得自签独立结论。

本轮计时证据为 n4 路径下 11 次 Blender（37.8 分钟）与 41 次 Cocos（26.7 分钟），合计约 64.5 分钟命令时长；它们覆盖的日历范围含未计时的编辑、观察、采集和空档，不能解释用户所见约八小时。下一轮先补全 `events.jsonl` 的整轮阶段墙钟，再判断瓶颈。建设新工具的优先级低于修复证据失效和减少重复全流程运行。

**具体调整**：① 视觉母版在固定机位局部预览达标后才进入 Cocos/全状态采集；② 正式构建只对应一个冻结的 candidate/build_id；先锁定源 ZIP，再由 manifest 引用其 SHA；包含 manifest 的最终审阅 ZIP 只在包外记录自身 SHA，避免循环哈希；③ 草稿按依赖失效集合重采，正式候选做一次完整覆盖；④ 每次低分返修保留原始命令、开始/结束、输入/输出 SHA、前后图和质量变化；⑤ 当 Q/哈希/构建绑定不一致时先修链路，禁止通过改分数或直接替换 SHA 消除错误。

### 可核算的下一轮目标

n4 已计时 Blender/Cocos 共 64.5 分钟。若在同等质量下把 11/41 次运行收敛到约 4–6/15–20 次，并假设各类运行耗时构成相近，命令时间预计减少约 **32–42 分钟**，仅占用户所述八小时的 **6.7%–8.8%**。完整轮次的首轮规划目标是 **8→6–7 小时（约 12.5%–25%）**，但必须另从重复采集/返工中实测省出约 20–90 分钟；否则按实际结果下调目标。**8→4 小时（50%）**需要在构建之外再消除约 198–208 分钟，当前没有证据支持承诺。

质量目标分两种：本次看图预评 ENV 75、UI 71.25、MIX 65 要分别提高 **15、18.75、25 个 rubric 分**才到制作侧 90；制作自评与本次预评的平均绝对差约 10 分，下一轮以 ≤5 分作为评分校准目标（偏差至少减少 50%）。真实正式结果以同一冻结候选的独立审核为准。详细公式、基线限制和日志要求见 n4 预审报告“下一轮量化目标与计算口径”。
