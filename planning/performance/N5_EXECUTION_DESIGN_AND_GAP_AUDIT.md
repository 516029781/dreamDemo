# n5 执行细化：减少重复运行、保住准确性

日期：2026-10-26。状态：**执行设计，尚未证明提速**。适用 `candidate_n5`；冻结的 n2/n4 源、构建和证据不覆盖。制作侧完整候选四卡各 ≥90，独立验收仍用当前 `art_review/rubric.json`。背景与缺陷关闭标准见 `art_review/reports/candidate_n4_provisional_20261026/REPORT.md`。若由多个子代理制作，文件所有权、并行批次、单点集成和资源锁见 `N5_PARALLEL_AGENT_PLAN.md`。

## 0. 对现有方案的审查结论

先前文档把 Blender 11→4–6 次、Cocos 41→15–20 次作为目标，但没有给出逐类变更的运行决策、现有工具的能力边界和证据失效处理。因此**它是试点目标，不是已落地的节省措施**。其他提法也有同样风险：一次全量采集、评分偏差减半、8→6–7 小时、三类哈希错误清零、性能不恶化，都需具体输入、动作、验收和日志；下文逐项补齐。目标次数不得作为质量失败时停止重建的硬上限。

实查现有入口：

| 能力 | 已有的东西 | 缺口及后果 |
|---|---|---|
| Blender 定向构建 | `tools/blender/run_courtyard_build.ps1 -Stage env_tree,map001` 可选择 Stage 并记秒数 | 该入口默认写 `art/full`；n4 改用 `tools/blender_n4/` 与 `art/candidates/candidate_n4/`。n5 需候选路径映射，不能把通用入口的结果冒充 n5；Stage 日志目前按固定文件名覆盖 |
| Cocos 构建 | `tools/cocos/build_web_desktop.py` 接受 `--project/--config/--log/--expect-output`，报告每次秒数 | 每次都构建 web-desktop，没有可用的“只编 UI”接口；应通过减少无效构建和复用一轮正式 build 降次数，不能假装它已有增量缓存。`--log` 要传唯一文件名，否则默认日志被覆盖 |
| 画面采集 | n4 `_v06_game_shots_n4.js` 一次取三张正式图；`_t6_all_states_n4.js` 一次取 41 UI 状态、34 资产和 24 动画帧 | n4 脚本写死 `n4` 路径、URL/端口和部分状态/输出；T6 没有按受影响状态筛选参数。n5 先复制并参数化，保留真实画布采集；不能复用旧构建截图 |
| 绑定与打包 | `producer_review.py`、Q/绑定校验器和源包脚本已有 | n4 绑定脚本从文件名排序猜“最新”构建，容易选错跨午夜的 build；源包脚本还收集持续变动的 `*.log` 和 JSON。必须显式传 build report、冻结输入清单及候选号，禁止 `glob[-1]` 充当版本身份 |

## 1. n5 运行单位：一个变更批次，不是一张截图

每次编辑前创建 `change_plan.json` 或 `decisions.jsonl` 记录：`candidate_id, run_id, defect_ids, changed_inputs(路径+前后SHA), change_type, affected_assets, affected_previews, affected_states, affected_Q, expected_visual_change, acceptance_observation`。一次批次只解决一个可观察的共享原因，可同时改多个属于同一母版的参数。完成后写 `observed_change` 和 `accept/revert/continue`；不能“改了文件”就自动进入 Cocos。

**判定优先级**：内容 SHA 变化及消费关系决定脏节点。mtime只用于发现候选变化；构建脚本、共享材质、相机、导出设置和工具版本也算输入。依赖关系不确定时保守扩大范围并记录原因，不允许凭文件名未变复用旧图。草稿可只重跑脏闭包；最终候选必须全量 Q、47 组覆盖、三正式画面、必要 UI 状态与包内外核验。

### 1.1 变更类型 → 最小运行 → 何时升级

| 本批改变 | 先做的低成本检查 | Blender 阶段 | Cocos 触发条件 | 草稿重采与失效项 |
|---|---|---|---|---|
| 主树枝干/叶簇/独立植被母版 | 单体源 PNG 与 n4/P1 局部对照，检查轮廓、悬浮叶和面数 | n5 的 `env_tree`；单体通过后才 `map001` 固定镜头 | map001 全景中轮廓、遮挡或密度确有改善，且要看真实游戏画布时 | 三正式镜头中的受影响画面、树前/树后 Q03、场景 Q06；共享树变动还使相关资产预览失效 |
| 铺地布局、花坛/长椅位置、背景层次 | map001 固定相机预览，检查可走路径和交互点 | 直接 `map001`；不为未变的所有小组件单独重建 | 布局预览通过；需要验证真实引擎材质和角色关系 | 正式全景、接近/遮挡相关 Q、布局与碰撞证据、ENV/MIX 自审 |
| 贴图或材质、场景灯光 | 材质近景或 Blender 场景预览；记录同一机位的色彩与预算 | 贴图只在被 GLB/Blender 母版消费时重建 map；纯 Cocos 运行时材质不跑 Blender | 一组材质/灯光改动达到近景目标后统一构建；最终判断以 Cocos 为准 | 相关材质近景、三正式画面、Q06/Q07、ENV/MIX 评分；相机/全局光变动则扩大到所有相关截图 |
| 纸面 SVG、字体、UI 布局 | `tools/ui_n5` 的组件/状态预览（先参数化 n4 入口） | 不跑 Blender | 对白、任务卡、交互按钮三类样板无明显遮挡/截字后 | 对白/HUD/暂停/竖屏受影响状态；Q05/Q09 与 UI/MIX 自审。脚本注入状态只能验证静态视觉，行为 Q 仍走真实输入 |
| 输入/暂停/方向逻辑 | 代码与状态转移表预检 | 不跑 Blender | 每个可运行修复批次构建并立即走定向行为回归 | Q04、Q09 及相关状态；从非出生点进入，禁止用 setter 直接制造目标结果 |
| 相机、角色 RT、全局色彩空间 | 先记录旧相机/配置 hash 与受影响矩阵 | 只有其输入依赖 Blender 输出时才跑 | 必须构建后看真实 canvas | 三正式图、Q01/Q03/Q06/Q09、全部相关视觉分；不能沿用原构图评分 |
| 仅报告文字、尚未冻结的评语 | 核文字与指向证据 | 不跑 | 不跑 | 若引用文件/评分/政策变了，重算报告和 manifest；冻结后改动则新候选版本 |

## 2. 为什么目标是约 4–6 次 Blender、15–20 次 Cocos

这是**可试验的运行预算**，来自 n4 实际 11/41 次，而不是对 n5 的质量限制。n5 先做三正式图缺陷诊断与低成本相机 A/B 灰盒，确定要使用的镜头；再分为树、远景/铺地、材质灯光、UI 对白与融合、行为/性能、最终综合批次。树单体预览约 1–2 次，完整 map 约 2–3 次，必要纠错 1 次，合计 Blender 约 4–6 次只是试点估算；若需要更多迭代以修复可见缺陷就继续。Cocos 在上述各批首次样板、必要纠错和综合回归时运行，目标约 15–20 次。**同一批可以多次编辑，但只有局部预览有清晰进步时才升级构建**。美术消融和批次内容见 `knowledge/N5_VISUAL_PRODUCTION_PLAYBOOK.md`。

每次 Cocos 构建前，执行模型必须在 `decisions.jsonl` 写：本次改变的文件及 SHA、上一轮截图观察、为何单体/静态预览不足、将查看哪些正式镜头/状态/Q。构建后写结果：`improved / unchanged / worse`、下一步。若三次同一问题没有可见改善，改几何或布局机制，不继续只调随机种子或色值。若用户要求的画面/行为仍有问题，即使达到次数目标也继续修，并报告超额原因。

示例顺序（不是现成一键命令）：

1. 先将 n4 脚本中候选路径、输出和端口抽为 n5 参数，确保产物只写入 n5。对三正式图做缺陷排序，在同一 n5 场景做相机 A/B 灰盒并记录 Q01/交互/遮挡代价；确定镜头后做树的原版/关闭体积 sprig/锚点补叶消融。树改变时运行 n5 `env_tree` 单体源及预览；不改善就换构造假设，不跑 map/Cocos。
2. 树单体与布局样板可接受后运行一次 n5 `map001`；同机位全景仍有明显空铺地或暗带，就修母版再预览，不启动 41 状态采集。
3. map 过关后运行一次 `build_web_desktop.py --project demo_n5 --config demo_n5/build-config-web-desktop.json --log <run_id唯一路径> --expect-output demo_n5/build/web-desktop/index.html`；保留返回的 JSON 路径和哈希，不按文件名猜最新。
4. n5 三镜头采集真实 canvas，并先看 ENV/UI/MIX 主体缺陷；若对白遮挡、场景重复或 Q04 行为失败，只重采受影响画面/Q。UI 静态局部预览无需重跑 Blender；但 Cocos/相机/全局光变化后正式 canvas 必须重拍。
5. 关键缺陷关闭后一次正式 build、完整状态/Q、评分和打包。若正式阶段发现新失败，按依赖规则返修并保留额外运行日志；不能为了达成次数目标保留失败候选。

**次数与时间的关系**：n4 记录的 64.5 分钟仅是 11+41 次命令时间。假设 n5 每类单次耗时结构相近，次数压缩约 50%–65% 才可粗估节约 32–42 分钟；若只省构建而审图、采集、返工没有改善，八小时整体仅约省 6.7%–8.8%。n5 必须分别比较总墙钟、构建墙钟、重采次数和最终画质，不能把目标次数当实际收益。

| 目标与当前缺口 | n5 具体执行 | 失败时回退/补救 | 可核结果 |

## 4. 需要先补的最小工具能力及验收

| 顺序 | 最小改造 | 目前状态 | 验收办法 |
|---|---|---|---|
| T0 | n5 候选配置/运行 ID：所有源、输出、端口、build report 从显式参数读取；禁用“排序取最新” | **未实现**；n4 脚本硬编码较多 | 对两个不同 run_id 的 dry-run/候选副本分别输出不同路径；绑定里 build_id 精确等于指定报告，而非文件名最新 |
| T1 | append-only 日志：Blender Stage 和 Cocos 每次 log 路径带 candidate/run_id；覆盖前拒绝或新建路径；将耗时与输入/输出 SHA 写事件 | **部分实现**：命令计时有，Stage/default 日志会覆盖；手工编辑/采集计时缺 | 连续两次运行后两份原始 stdout/stderr 和 JSON 都存在，SHA/退出码可回查；`events.jsonl` 能还原整轮墙钟 |
| T2 | 受影响集合清单：按上表从变更源导出需重建的 Stage、画面、状态和 Q；未知依赖采取保守范围 | **文档规则已有、自动执行未实现** | 单树、UI、相机三种变化分别得到不同闭包；最终阶段仍显示全量验收计划，不漏共享依赖 |
| T3 | n5 定向采集参数和最终全量模式；正式输出带指定 build_id | **三镜头/全量脚本分别有，候选参数化与筛选未实现** | 定向采集只产生指定状态；最终模式产生合同所需全部状态；源与 build 改变时旧图被拒绝引用 |
| T4 | 冻结/打包预检：显式 source ZIP→manifest→外层 review ZIP 顺序；校验 SHA/CRC/缺失/重复 | **现有零散校验，n4 仍漂移** | 用 n4 已知三种错误作只读负例均报 fail；新候选完整包检查通过且原文件不被覆盖 |

先补 T0/T1 的最小版本再开始 n5 大量尝试；T2/T3 可先由人工 `change_plan.json` + 现有三镜头/定向 Q 脚本执行，待首个真实重复瓶颈出现再自动化。不要为此先造一整套新平台。T4 必须在首次正式冻结前可用。性能试点将工具开发成本计入整轮，不能把改工具的时间藏到基线之外。

## 5. 与旧方案冲突的修正

`END_TO_END_DEVELOPMENT_CHAIN_PLAN.md` 旧第 6 节写“先生成 manifest，最后生成 ZIP”，与 n4 **manifest 引用源 ZIP 的 SHA** 相冲突。准确顺序是：所有可编辑源/截图/Q/评分锁定 → 源 ZIP → 源 ZIP SHA → manifest → 可选包含 manifest 的最终审阅 ZIP → 包外 SHA。最终审阅 ZIP 不得被其内的 manifest 自引用。`make_n4_source_pack.py` 还收集会继续变化的日志/JSON，n5 应将执行日志独立于源 ZIP，或在收录前完整冻结它们；无论采用哪种，都必须在清单写明并核验。

此文件定义**如何做**；次数和比例是试点目标。只有 `candidate_n5` 同范围实测并达到美术/机械标准后，才能把目标改写为已实现收益。

## 6. 批次自我学习的新增执行要求

每个 n5 变更批次按 `planning/execution/SELF_LEARNING_LOOP.md` 执行：开始时只检索相关经验；编辑前在 `performance/decisions.jsonl` 记缺陷、原因假设、预计改善、固定验证画面/状态及潜在回归；局部预览后不看自己的解释先找反例，再记录预期与实际差异。失败则改原生源/方法并重测；批次结束把可推广规则作为 `proposed` 写入 `planning/execution/LESSONS.md`。候选冻结前抽查未重点修改区域、UI 边界、角色同屏状态和证据链。该步骤使用现有日志，不额外增加全量构建；预期收益需在 n5 用漏检数、自评与独立分差、返工次数和端到端墙钟验证，不能提前宣称提速。
