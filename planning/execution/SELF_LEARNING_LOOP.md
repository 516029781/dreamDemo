# 制作侧自我总结与问题发现闭环

更新：2026-10-26。适用当前 `candidate_n5` 及后续制作候选；这是制作流程，不修改合同、rubric、90 分筛选线或独立审核权限。所谓“学习”是把实际失败转成可复用的制作规则、检查和案例，**不是**修改模型权重，也不是让模型自评自签。

## 1. 每个变更批次都执行的闭环

1. **取回经验（开始前，限 5 分钟）**：读取活动返修指针、最新独立报告、本协议及 `planning/execution/LESSONS.md` 中与本批资产/缺陷匹配的条目。只取相关经验，记录采用、暂不采用及原因；历史经验若与当前实图或合同冲突，以当前证据和生效合同为准。
2. **写可证伪预期（编辑前）**：在候选 `performance/decisions.jsonl` 追加一条：`run_id`、缺陷 ID、基线图/状态及 hash、观察到的差距、原因假设、拟改原生源、预计改变的轮廓/材质/UI/行为、固定机位或状态、最小检查、可能回归的邻接区域。禁止只写“优化美术”“提升质感”。
3. **做最小修改和局部检查**：保留命令、UTC 起止、退出码、输入/输出 hash 和原始日志。先单体或同机位预览；仅出现预期改善才升级受影响构建与采集。正式候选仍需完整 Q 和绑定。
4. **主动找反例（每批预览后）**：先遮住自己的修改说明，按 P1、上一候选、当前候选同尺寸比较；再检查非目标区域和真实运行状态。逐项问：哪处比之前更差？角色与环境是否割裂？换镜头/对白/暂停/竖屏后是否仍成立？源、build、capture 是否同一版本？把新发现写入问题记录，不能因原缺陷变好而忽略回归。
5. **对照预期**：在同一 `decisions.jsonl` 追加结果事件，引用前述 `run_id`、前后图与 hash、观察、目标是否达成、出现的新缺陷、下一动作。未改善要写清假设被什么证据否定；连续三次同问题无可见改善，停止同类参数微调，转到拓扑/构图/渲染机制诊断，其他可做任务继续。
6. **返修并验证**：严重问题、Q/绑定失败、低于提交门槛时，改原生母版并重做受影响检查。行为/证据链问题加一个可重复的负例检查；视觉问题至少保留固定机位的前后原图和独立一次“找反例”记录。不能仅改分数、评语或 hash 文本。
7. **批次末总结（约 5 分钟）**：记录本批原计划与实际耗时、无效构建/采集次数、发现/关闭/新增缺陷数、哪条旧经验有效、拟提炼的新规则。把可复用规则提案写入 `planning/execution/LESSONS.md` 的待验证区；一次成功只能称“候选经验”。

## 2. 候选冻结前的逆向自审

同一个制作模型另起一次审查视角，但身份始终是 `producer_self_review`。先看原尺寸 P1 对照和真实 canvas，再看实现说明；逐维填可见差距、证据和分数。对每个拟给 4 分的维度，找至少两个相关机位/状态和一个最可能失败的反例。先写观察再算分，保留初始分与修订理由。机械检查只证明结构/哈希/Q，不证明审美。

审查至少做四类抽查：① 抽一个未重点修改的 ENV 区域；② 抽一个 UI 边界状态；③ 抽一个角色与环境同屏动作/遮挡；④ 逐条追踪源 ZIP、manifest、Q 对照图、行为结果、正式截图的 hash/build_id。任何严重新问题返回制作侧，不通过改评分或删除问题绕过。制作侧通过后仍由独立审核者给正式结论。

## 3. 经验如何入库、如何失效

`planning/execution/LESSONS.md` 是短小的经验索引，不存大段运行日志。每条包含：ID、状态 `proposed|validated|retired`、适用触发条件、失败症状与原图/日志路径、被证据支持的原因、有效改法、最小复核、反例/不适用条件、来源候选、复核结果。来源证据保存在候选目录，经验条目只引用路径。每次独立审核后，按“先前预测的问题是否被发现、独立新发现是否未覆盖、修复是否回归”回写。

当一条经验需要多步操作示例或完整失败案例时，在 `knowledge/RECIPES.md` 或 `knowledge/CASEBOOK.md` 增加入口和证据状态；`LESSONS.md` 继续保持唯一短经验索引，不另建第二本规则账。开始新批次可从 `knowledge/README.md` 按问题检索。

首张地图成功后的跨地图模板提炼按 `POST_SUCCESS_MAP_REUSE_PLAN.md` 执行；当前每批留下原始事件、决策和可编辑源关系是其输入。首图通过可形成候选模板，第二张不同布局地图完成重建和引擎验证后才称流程已复用。此后续工作不成为当前 I07 美术候选的中途等待门。

只有在相同缺陷有前后证据且目标检查通过后，才能把提案标为 `validated`；涉及审美的规则还应得到后续独立审核或跨候选复验。若产生回归、与新合同冲突或无效，标 `retired` 并写原因，不删除历史。优先把反复出现且可机械检查的问题变成脚本负例；主观视觉判断仍保留原图和人工/独立复核。

## 5. 最小交付与检查

每批至少有 1 条编辑前假设、1 条编辑后结果、1 张前后同机位对照或等价行为/绑定证据、1 条主动找反例结论；无新经验也写“无可推广经验及原因”。完整候选须附批次总结和待验证/已验证/失效经验列表。缺记录要补真实事实，未知时间标 `unknown`，不能事后虚构日志。经验记录缺失本身不改变现有 `producer_review.py` 门槛；工作包交接时如实标记“自我学习记录未完成”，不能声称闭环已执行。

## 6. 依据与本项目化边界

- OpenAI Harness Engineering：把反馈写回仓库文档或工具，能机械化的规则转为检查；本项目对应经验索引与负例回归。
- OpenAI Agent Improvement Loop：把 traces、反馈、eval 和下一轮 harness 修改连成回路；本项目对应 `events.jsonl`、缺陷/评分证据、改法与复验。
- OpenAI Iterative Repair Loops：review→repair→validate，验证残余问题作为下一轮输入；本项目对应批次逆向自审、原生源返修、定向与最终复核。
