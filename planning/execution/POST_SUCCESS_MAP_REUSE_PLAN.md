# 首张合格地图完成后的链路沉淀与跨地图复用

更新：2026-10-26。当前范围仍是 `art_required/I07` 的庭院完整美术候选。本计划规定**从现在开始留什么记录**、首张地图合格后提炼什么，以及如何证明可用于下一张地图；不增加 I07 的中途审核阻塞，也不宣称地图工坊 M0 已实现。

## 1. 当前记录状态：要求已写入，n5 实际轨迹尚未开始

截至本次检查，n4 留有 `delivery/performance/` 的单次 Blender/Cocos 命令 JSON、`art_review/reports/candidate_n4_provisional_20261026/time_audit.json`、截图/预审报告和历史候选证据。`planning/execution/LESSONS.md` 与 `knowledge/RECIPES.md` 记录了**待验证做法**。它们能解释部分失败，但缺连续编辑、观察、等待与返工墙钟，不能还原完整八小时。

当前尚无 `delivery/next_cycle/n5/performance/events.jsonl`、`decisions.jsonl`、`commands.txt`、`summary.json`，`tools/blender_n5/`、`tools/ui_n5/`、`demo_n5/` 也尚未创建。T0/T1 日志与候选参数化在执行设计中仍标为未实现/部分实现。因此现在不能说“n5 已在自动记录完整制作过程”。执行模型启动 n5 时，先建立候选基线和唯一日志，再做原生源修改；旧 n4 记录仅作历史参照，不补写成 n5 实时事件。

## 2. n5 运行中必须采集的可复用信息

| 记录 | 最小字段/证据 | 为什么下一张地图需要 |
|---|---|---|
| 候选基线 | 来源候选、每个可编辑源路径与 SHA、工具版本、相机/灯光/坐标约定、有效合同版本 | 知道成功结果从什么可重建输入产生；不用猜“最新文件” |
| `events.jsonl` | agent/run、阶段起止 UTC 与单调耗时、资源锁、输入输出 SHA、退出码、原始日志路径、等待/unknown | 分辨制作、构建、采集、返修和合并的关键路径；比较跨地图工期 |
| `decisions.jsonl` | 缺陷和 rubric 维度、编辑前假设、修改的原生母版、固定镜头/状态、预期变化、实际前后图与反例、保留/撤销及原因 | 把有效构造机制与无效尝试分开；避免下一张地图重试随机细节 |
| `commands.txt` 与 `logs/` | 实际命令、工作目录、参数、工具版本、stdout/stderr、退出码；每次重试独立 run_id | 别的模型能重跑、定位失败，而不是照口述猜工具用法 |
| 地图数据与资产关系 | `map_id`、布局 revision、资产/实例稳定 ID、碰撞和站位、可编辑 `.blend`/SVG/纹理源、导出 hash、Cocos 场景引用 | 把“画面风格母版”从“庭院特有位置”分离，迁移至新地图 |
| 正式证据 | 唯一 build report/build_id、三正式原图、受影响状态/Q、全量 Q/47 组、评分、manifest/包 SHA、独立报告 | 只有同源且审核通过的结果可当成功案例；局部试件仍标试验 |

日志中的 `unknown` 必须保留，不事后虚构。截图注明来源场景、相机、分辨率、状态、build_id、布局 revision 与 SHA。P1 风格原帧是参考，不标作本地图同机位。子代理的记录可并行写到各自独占文件，集成人按 `run_id` 汇总，不让多进程写同一 JSONL 造成行损坏。正式记录从候选开始时产生，不能在交付后补造完整轨迹。

## 3. 首张“合格”之后的提炼次序

“首张合格”至少指：I07 完整制作侧筛选通过、Q/绑定与源包同源、严重开放项为零；独立审核随后确认美术候选通过。制作侧完成时可先写**草稿配方**，独立结论未出前不得标 `validated` 或宣称质量已独立证明。若独立审核退回，先按原候选返修并将失败写入案例；修后的成功源才可作为模板基线。

1. **冻结成功样本**：保留成功候选的源、构建、原图、Q/评分、批准记录与 SHA。输出一张“输入→工具→导出→Cocos→截图→审核”的依赖图，标清哪些环节自动、哪些人工判断。
2. **拆分不变量与地图参数**：从代码里抽出可复用的相机/尺度/色彩/灯光、地砖/树/道具/纸面 UI 母版、导出与证据检查方法；把庭院独有的地形轮廓、道具坐标、剧情文字、交互站位与 NPC 位置留在地图数据。不要把 `candidate_n5` 路径、庭院坐标、资源 ID 或固定端口硬编码进通用工具。
3. **建立模板包**：在成功之后创建版本化 `templates/map_art_v1/`，至少包含：空白地图项目说明、`map_project.json`/`layout.json` 示例与字段校验、母版资产清单和来源状态、Blender→Cocos 导出配置、UI 状态母版、相机/光照预设、采集/Q/绑定脚本参数、运行命令和已知限制。只打包自有可编辑源与确认可复用的依赖；第三方研究参考不进入可发布素材包。
4. **形成操作用例**：把 n5 的有效做法写入 `knowledge/RECIPES.md`，失败修法与反例写入 `knowledge/CASEBOOK.md`，短经验状态只在 `planning/execution/LESSONS.md` 维护。每条都关联成功候选的真实图/日志/审核结论、适用条件和不适用情况；不把一次局部成功推广成所有地图必然有效。
5. **提炼可编辑地图入口**：按 `MAP_WORKBENCH_EXTENSION.md` 的 M0 合同检验保存重开、稳定实例 ID、坐标/碰撞/站位、导出与 Cocos 重导入。若 M0 此时仍未实现，模板包必须明确“脚本+Blender 操作”能力及缺口，不能把方案写成已存在的地图编辑器。
6. **做第二地图迁移试验**：选一个与庭院结构不同的小区域，仅复用模板工具和风格母版，重新填写 `map_id`、布局、资产实例与交互点；完成保存重开→导出→Cocos 可走→三视图/界面→Q/来源检查。不得直接复制庭院成品几何冒充跨地图复用。记录必须改动的通用代码、人工步骤、失败点和时间，修模板后再重试。

## 4. 什么时候可称为“可复用链路”

首张地图独立通过后，只能称为**一套成功样本和候选模板**。只有第二个不同布局的地图在同一模板下完成可编辑源→导出→引擎预览/可走→证据检查，且没有为它复制一套硬编码流水线，才把链路状态标为 `reused_once`。若需要对第二图做完整风格合格声明，按第二图当时有效的美术合同与独立审核执行；`reused_once` 本身只证明工具/流程迁移，不等于第二图已获最终美术放行或微信发布。

最小复用验收报告列出：模板版本、两张地图各自 `map_id/layout_revision`、可编辑源与导出 SHA、共用脚本比例（按实际共享文件列，不凭行数杜撰百分比）、新地图专属数据/资产、完整步骤与命令、手工干预、失败/返工、墙钟及关键路径、画质与性能、未测事项。若第二图必须修改通用脚本，说明是合理扩展还是庭院硬编码，回写模板版本和回归测试。成功经验状态继续区分 `proposed`、首图独立验证、跨地图复用验证。

## 5. 排程关系

n5 制作时必须**同步留原始记录**，因为事后无法可靠重建尝试顺序和耗时。首图完成后的模板提炼与第二图试验是后续工作；它们不作为当前 I07 请求集中审核的前置条件，不让“先造通用平台”拖住首张合格地图。独立审核可在候选完成后与草稿配方整理并行，但只有审核结论通过才将该候选标为成功样本。
