## 最终画面定义

目标是一块在微信小游戏里可行走的秋日广场：浅暖色的大石板组成连续道路；台阶、栏杆、花坛与设施构成可理解的空间；金橙色树叶有分枝、叶团、亮边和透光空隙；枯草在种植区成片生长；角色在游戏尺度下清晰并接地；阴影有方向且保留细节；常态、交互和对白 UI 不破坏主体构图。场景使用我们自己的布局与可编辑母版。

**交付场景**：一块完整、可行走的秋日广场。运行时相机跟随玩家；玩家从入口走过石板路，到达一个可交互设施，触发对白，再返回。树、草、设施、角色和 UI 在全过程保持同一画风。需同时展示整画面、局部材质和角色移动，单张摆拍不算完成。此目标是本期美术竖切片；后续整张地图可以复用通过验收的母版。

**验收定义**：一张固定的 t084 主参考；我们在固定的**验收锚点**采无 UI、常态、交互图，这三张需记录同一世界状态、相机模式、预设、位置、朝向、FOV、画布尺寸和 DPR。对白可能改变相机俯仰，单独记录对白机位及 UI 状态，不伪称四张同一相机矩阵；若交互本身触发 inspect 机位，也须单独记录并补拍锚点对照。另交一段完整往返录屏，覆盖所有正式相机状态；可编辑原生源、来源/许可清单、原生源→导出→构建→截图哈希、视觉自评和微信真机结果。制作侧仍按有效规则每卡至少 90 分筛选，Q/绑定通过且无未解严重问题后再集中独立审核；视觉 90 不是“与截图像素相同 90%”。手机性能目标须在指定设备上实测，不能由桌面浏览器模拟器推断。

### t084 到我们场景的构图样板

先用灰模在**验收锚点**锁住画面的大面积关系，再做材质：角色是中部视觉焦点；连续道路与前景台阶/栏杆引导行走方向；树冠占上部形成透空的暖色边界；种植容器与成片草占侧边，不能只散落几簇；中景设施构成明确的交互目的地；远景建筑只提供空间层次，不抢角色。对照图上给这六类区域画半透明框，记录各自的屏幕占比、遮挡关系与留白。布局属于我们的地图，不按参考图像素坐标复刻；角色、路、交互目标与 UI 在手机尺寸下仍须同时可读。灰模不满足这些关系时先重排构图，不进入树叶和纹理精修。

| 层 | 当前主要差距 | 目标与验收画面 |
|---|---|---|
| 铺地 | 小砖、随机明暗格与大板方案并存，接缝密度跳变 | 同一主铺法、尺寸和走向；配套台阶与收边。磨损按动线/边界分布，不出现棋盘格或孤立污点。先锁一块样板，再复制到全图。 |
| 树 | R 版有叶形但树冠过大、过密，边缘碎；C 版多面体感强 | 一棵树先过四视角及正式机位：主枝可读，叶团大小错落，内部留空，亮部金橙、暗部暖棕；不露光滑球芯或明显重复卡片。 |
| 草 | 成片覆盖不足，尖角草均匀散布或压到砖面 | 3–4 种可编辑草簇，以花坛/种植槽多边形成团布置；高低、方向和受光有变化。草根落硬质砖面数为 0，游戏机位中能读成连续草丛而非零星尖片。 |
| 色彩与光 | 黄褐占满画面、亮部不足或局部阴影近黑，前后景分不开 | 先用中性亮石板与暖色植被分配面积，再调光照/雾/后处理；暖高光、暖棕暗部有细节，少量冷色提供距离感。禁止只凭全局加饱和度过关。 |
| 构图与设施 | 主树压住活动区，地面空而远景块体破碎 | 在固定验收锚点比较构图，并检查完整跟随路线；道路、角色、交互目标可读。背景有真实设施剪影，前景遮挡受控；先修形体，再处理材质细节。 |
| 角色与 UI | 角色画法精度高于环境；纸面 UI 占画面过大 | 保持锁定角色源，校角色比例和接触影；任务、交互、对白分别检查，不遮挡路径与角色。 |

### 单资产试装流程（扩批前必做）

1. 从 Kenney 选 **1 件设施**，从 Quaternius 或 Poly Haven 选 **1 棵树/枝形和 1 簇草**；下载原件并登记 URL、CC0 页面、文件 SHA、格式、面数、贴图大小及选它的理由。若一个包没有合适物件，记录淘汰原因，不因已下载就使用。
2. Blender 导入后统一米制尺度、朝向、原点、命名和碰撞；建立我们的材质实例。树叶用可编辑图集/叶形，草用可编辑簇母版，石板只使用一种主铺法。每件保存 `source`、`adapted.blend`、`runtime.glb` 三层关联，禁止只保留最后导出的 GLB。
3. 先做灰模和单件 1280×720 游戏机位图，随后做包含地板＋树＋草＋设施＋角色的组合图；与 t084 原图并排。分别检查形状、色彩、密度、尺度、角色焦点和种植合法性。视觉不匹配时先改母版；仍不匹配则弃用该外部源。
4. 运行时仅加载实际使用的子资产，做低模/LOD、材质合并、贴图图集、实例化和受影响区域构建；比较新增前后的三角面、绘制调用、纹理/缓冲占用、GLB 字节。试装通过后才把同一规则扩到整张图。
5. 在微信真机上尽早跑同一画面和往返移动。记录设备型号、画质档、分辨率、热机后的帧时间与失败现象；真机未测只能写 `pending_device_test`，不能写“微信可用”或据此冻结全量方案。

**真机测量口径**：单资产试装前先指定一台验收用中档手机，记录型号、系统/微信版本、屏幕像素、DPR、画质档及测试日期。以正式玩法路线连续往返，覆盖最密树冠/草丛、交互和对白；预热后记录至少 3 分钟的逐帧耗时、内存峰值、包体与画面录屏。30 FPS 目标对应帧时间约 33.3 ms；统计 p50/p95、卡顿次数和设备温度，不能只报瞬时 FPS。若 p95 超过 33.3 ms 或出现显著卡顿，先按纹理、植被 overdraw、三角面/绘制调用、阴影逐项定位，再做不损害 t084 整画面的 A/B 降档。最终档位同时通过画质复核才算合格；没有设备时保留待测状态，不以桌面 SwiftShader 的 2.9 FPS 推算手机结果。

### 镜头可见性与像素预算

P1 的 1920×1078 是**参考视频截图的尺寸**，不是运行贴图或手机内部渲染必须达到的尺寸。项目目前 UI 设计分辨率是 1280×720，运行画布会按窗口调整；正式性能试验必须记录实际画布像素和设备 DPR，不能把 1280×720 的设计坐标当作 GPU 实际输出分辨率。**分开降低 3D 内部渲染分辨率、保持 UI 原分辨率是待实现的优化选项，不是当前能力**：现有角色 1024×1024 RT 不等于整个 3D 主场景 RT。只有完成渲染管线兼容试验、同画面 A/B 和真机 UI 清晰度检查后，才能采用这个选项。

项目的游戏相机会跟随玩家移动，且有 inspect/对白机位。因此**只在一张 t084 对照截图中不可见**，不代表整个运行过程永远不可见。可删或简化的范围必须由“玩家完整可走路线 × 所有正式相机状态”的可见区域并集决定。镜头外物体若会投影到可见地面、参与遮挡或碰撞，也要保留相应的低成本代理。固定背面若经全路线验证永远看不到，可删背面面片或只保留遮挡/阴影代理。

| 内容 | 预算规则 | 验证方式 |
|---|---|---|
| 模型几何 | 近景以实际屏幕轮廓为准；小于一个屏幕像素的倒角、裂缝、叶脉改为材质或删去。远景做 LOD/代理；重复物件尽量共享网格与材质 | 玩家走完整路线，记录近、中、远三处截图；检查剪影、LOD 切换、阴影与三角面 |
| 贴图像素 | 按物件在**最近可能机位**的最大显示尺寸选择导出尺寸；先试约 1–2 倍的屏幕采样密度，再看压缩与 mip 后是否糊。数百像素宽的物件先试 256/512 或 1024，而不是直接用 4K/8K；可重复石板用少量可平铺纹理 | 同画布下比较 1×/2× 来源贴图和运行压缩格式，记录画质、纹理内存、包体 |
| 植被 | 主树保留可读轮廓，内部叶脉/小枝可烘进叶图集；远树用低模或有限朝向的叶卡。草按簇渲染，近草保留形，远草只保留色块和剪影 | 全路线观察草不突变、不透明矩形不露边；检查 alpha overdraw 和 draw calls |
| UI/角色 | UI 字体与图标保持手机可读；3D 降分辨率不得连带把 UI 模糊。角色 RT 当前为 1024×1024，只能在实际显示尺寸、动作边缘和性能测量后决定是否下降 | 常态/对白/移动截图，角色轮廓、文字与触控面积均通过 |

先做“保持画面不变，只降运行成本”的 A/B：不改相机和构图，分别测试贴图降档、叶/草 LOD、背景简化、阴影贴图档位及实例化。每个选项保留回退开关；当省下的成本肉眼可见地损坏 t084 目标时，应换优化方式，而不是让画质验收迁就预算。

## 制作与审核顺序

0. **统一验收工具配置**：在新候选取证前，把正式对照图、风格测量、自评和证据生成脚本中的**整画面主参考**统一为 t084 路径及上述 SHA；旧 t015/t044 结果只标记为历史或专项用途。跑一次预检，输出每个脚本实际使用的参考路径、SHA 和裁切框；任何脚本仍把旧帧当整画面主参考，就先修脚本，不能启动正式自评或冻结。变更仅作用于新候选，不重写旧冻结证据。
1. **锁参考和验收锚点**：验证 t084 哈希；固定锚点的角色世界位置、游戏相机模式/预设及 1280×720 截图方式，记录实际相机矩阵与画布像素。保存当前正式画面为返修前基线。R/O/C 试验图只用于选方法，不与旧正式截图混写成同一个候选。
2. **素材入围与构图**：做上文三件开源素材的来源/成本表；用灰模检查行走通道、树/设施/前景占位。若现成模型破坏 P1 大形，立即弃用或只取其可编辑部分。
3. **地板与设施样板**：定唯一石板模块及台阶/收边；小设施统一比例、材质和损耗。先在游戏机位验证整画面，不用随机纹理填空。
4. **单树与草簇样板**：分别用可编辑 Blender 结构、叶图集和草簇变体制作；先检查近景、剪影、四视角和场景机位，再扩到地图。种植坐标使用容器边界审计。
5. **统一光色**：在几何与覆盖率稳定后比较 t084 的对应区域，调整材质、主光、环境光、阴影、雾；后处理只做最后的小幅统一，不代替材质和模型修正。任何新后处理/alphaTest 改动先在微信端做最小兼容性试验，失败时回到可编辑材质或叶形母版，不能降级为露出矩形卡片。
6. **UI 合成、行为与真机**：提交锚点无 UI、常态 UI、交互图及有相机参数记录的对白图，另交一段角色往返移动画面；记录移动时的遮挡、接地影、可读性及微信真机成本。低分继续由制作侧返修，完整候选通过现行 90 分自审筛选后再集中独立审核。

每批必须留下改前/改后图、t084 原图或标框裁切、修改的原生源与参数、构建/相机 ID、失败反例和下一批决定。不得把尚未实测的预测写成通过，也不得为达旧数值阈值牺牲整画面。

## 现有方案审查与优先级

现有文档覆盖了素材制作和机械检查，但**尚未满足“固定参考图、整画面效果一致”的要求**，原因如下：

1. `P1_STYLE_SPEC.md` 把五帧平均值当风格目标，`N5_ART_FIX_PLAN_20261027.md` 主要测 t015，`make_n5_comparisons.py` 又分别用 t015/t044/t084；这些可作为历史研究，不能继续让执行模型自由换整画面锚点。下一次正式对照图一律把 t084 放第一栏。
2. 调色方案存在方向冲突：旧规格强调把暗部压深，新修正方案测出树冠需要提亮。先用 t084 的树、草、石板区域在最新正式引擎图中重测，再做 A/B；旧 hex 和灯强仅作试验起点，不能同时作为硬规定。
3. `DETAIL_DENSITY_RULES.md` 建议减少碎叶和小砖，新修正方案又要求更密的草。两者并不必然冲突：**扩大单草簇覆盖、减少孤立细片**，按游戏机位检查草丛整体密度与边缘噪声，不能只用叶片数量判断。
4. 多份方案重材质/颜色而轻整画面构图。t084 的台阶、栏杆、种植容器、背景设施和角色留白共同决定风格；地板、树、草达标但背景仍是破碎土丘时，MIX 仍不能通过。
5. T5 的 R/O/C 是同一构图的试验，尚未与当前正式 UI、对白、行为及手机运行证据绑定；选中某试验方案不等于完成候选。先选视觉样板，再按同一源构建并采集正式证据。

本文件对**当前视觉目标和参考取样**优先于旧计划中的多帧平均和临时变体说明；不改变 `art_review/harness_contract.json`、`art_review/rubric.json`、角色来源、旧冻结包或任务账本。若合同中的历史参考列表另有用途，保留该记录，正式独立审核按合同执行，新增的 t084 主参考须在提交说明中清楚标注。
