## 0. 结论先说

1. **明日方舟没有可商用的开源地图或美术资源。** 存在的是社区解包（2D 关卡网格 JSON、立绘/图标图集）和查看工具，版权归鹰角。官方同人条款明确禁止"直接使用游戏内素材做复制、扫描、采样"，且只允许非商业。**只能当参考，不能进包。**
2. **但它的技术方案是公开的。** 2020 年 Unity 线上技术大会，鹰角黄一峰讲过完整的 3D+2D 方案：PBR 场景、静态烘焙 lightmap+shadowmap、运行时一盏动态光、**静态合批到 draw call 个位数**、角色 Spine + Unlit、tint color + 后处理融合。**这份公开演讲比任何解包素材都值钱**，第 2 节完整拆。
3. **我们的架构在"组合"上是主流的，"实现"上不是。** 「3D 环境 + 2D Spine 角色」是二游标准解，我们角色侧已经和方舟完全同构（930 KB Spine → RenderTexture → 世界面片）。不主流的是场景侧：**代码生成 905k 面、无烘焙、540 draw call**。方舟同类场景靠静态合批是个位数 draw call，我们差 50–100 倍。
4. **面数不是包体问题的核心，属性格式才是。** 把 70 MB 的地图拆开，68.9 MB 全是 float32 顶点属性，其中 12.6 MB 是**已经不再使用的顶点色**。不改美术、不改布局，只做属性手术（去 COLOR_0 + 量化 + MeshOpt）能压到 **16–18 MB**（5 节有实测推导）。
5. 推荐顺序：**路线 0（属性手术）→ 路线 A′（方舟式收敛：烘焙 + 合批 + 图集）→ 路线 C（2.5D 兜底）**。前版把 C 排在 A 前面，看过方舟方案后改回来：我们要补的正是"便宜地做 3D 场景"这件事，C 是绕开它而不是解决它。
6. **已定：O/C/R 三档不保留，只做单套风格。** 好处是烘焙只需烤一遍，路线 A′ 第 2 项成本减半。
7. **实测修正**：铺装只有 **1,800 三角面**（占 0.25%），draw call 的真正来源是 **10 个叶材质 × 每片树冠 = 242 个 primitives（54%）**。详见 `planning/art/ARKNIGHTS_MAP_DECOMPILED.md` 第 6 节——**要治的是材质数，不是石板几何。**

## 2. 调研二：明日方舟本体的美术技术架构

来源：鹰角网络 黄一峰《明日方舟中 3D 和 2D 结合方案》，Unity 线上技术大会 2020；以及立项复盘访谈。以下全部是官方公开表述。

### 2.1 场景：标准 PBR，块面化雕刻，风格化贴图

- **工作流**：标准 PBR。3D 网格状地图（tile 化）、地图周边摆件、背景远景、可交互/装饰小物件，全部 3D。
- **造型**：块面化的雕刻，做风格化处理。**关键一句：不追求"以较低面数实现卡通效果"，面数相对较高。**
- **贴图**：风格化的贴图绘制，不追日式 RPG 那种卡通化。
- **Shader**：基于 Unity Standard Shader 改的自定义 PBR——微调 BRDF2 优化性能，加**可着色阴影**、加**高度图**，适配场景特效。

### 2.2 光照：烘两张图，运行时只留一盏

- 每个场景用 Unity **静态烘焙**，烘出 **Lightmap + Shadowmap 两张**。
- **运行时只有一盏动态光**（给场景里的动态物体），其余全靠静态烘焙光；特殊情况加光照探针做静态反射。
- 这就是为什么"阴影看起来细腻"却不耗性能：**阴影不是算出来的，是贴上去的**。

### 2.3 Draw call：个位数

- 整个场景是静态的（连光照贴图和阴影贴图都是静态的），靠**静态合批**，正常渲染时"**绝大部分场景的 DrawCall 都在个位数**"。

这一条是整份演讲里最该划重点的。我们同规模的场景是 **540**。

### 2.4 单位：Spine + Unlit，是"效果选择"不是"技术受限"

- 角色、敌人、第三方单位、可交互 2D 物件——**全部 Spine 骨骼动画**，**Unlit shader**，不受任何动态光照/阴影影响。
- 官方明确说这不是技术妥协：实验过让 2D 角色接受场景光照，**辨识度会变差**，玩家难以快速分辨需要关注的目标。
- **正反两套 Spine**：大部分干员做了正面和反面两套工程，翻转时用类似《纸片马里奥》的"纸片人"翻转。理由：单面角色在冲刺、穿刺这类方向性强的动作上会穿帮，为了避免穿帮只能把技能设计成"圆弧斩"这种模糊方向的招式，**会反向限制策划和美术**。次要单位用单面省资源。

### 2.5 3D 场景 + 2D 角色的空间关系（这段是硬核经验）

- 相机与场景 XZ 面呈 **60°**；2D 角色要正对相机（billboard），所以角色相对场景法线**倾斜 30°**，实际是"斜插"在场景上。
- **穿模**：地块模型一高就穿。
- **错误解法**：关掉 z-test，把场景/摆件/角色手工做深度排序。能解决穿模，但**破坏静态合批**（draw call 暴涨），而且跨格点的摆件（比如树）根本排不清前后。
- **正确解法**：在 Vertex Shader 末尾把深度变换到**垂直于场景的空间**，欺骗深度测试和深度写入。高度 ≥ 0 用这套；高度 < 0（比如杜宾向下挥鞭）让鞭子旋转到平行于 XZ 平面。
- **Lightmap 跨平台一致**：Unity 2017 LTS 上 Lightmap 编码 PC 是 RGBM、移动端是 dLDR，dLDR 会丢 alpha、吃掉阴影细节。解法：TextureType 从 Lightmap 改成 Default，shader 里用 RGBM 解码，把 alpha 抽出来塞进 shadowmask 的 green channel（red 已被占用）——顺手省了张图的 alpha。
- **3D/2D 怎么融**：每个主题定义一套 **tint color 作用到所有单位**，让 2D 角色的着色贴近场景氛围；再加 **color grading + Bloom + Vignette** 后处理；最后把这几个旋钮交给美术调。

### 2.6 关卡是数据，不是手工摆的 3D

关卡定义就是一个二维数组：

```json
{ "heightType": 0, "buildableType": 1, "tileKey": "tile_road",
  "passableMask": "ALL", "isStart": false, "isEnd": false }
```

- `tileKey`：`tile_road` / `tile_wall` / `tile_forbidden` / `tile_start` / `tile_end` / `tile_floor`…
- `heightType`：`LOWLAND` / `HIGHLAND`（0/1），换算是 `z = heightType * -0.4`
- `buildableType`：`NONE` / `MELEE` / `RANGED` / `ALL`
- `passableMask`：`ALL` / `FLY_ONLY` …
- 关卡级还有 `width` / `height` / `view`（相机位置 + 目标）

**美术只做 tile 的 prefab，关卡是几十行 JSON。** 一个新关卡的成本是"摆格子"，不是"建场景"。

### 2.7 UI：为什么它成了国内游戏 UI 的标杆

- **配色克制**：主界面 90% 是不同明度的灰，关键按钮深蓝，**只有紧急通知才用红**。
- **磁带盒未来主义**（cassette futurism）：少即是多，黑色长条做主视觉，半透明塑料质感，符号化排列，几何外形。形式追随功能。
- **字体分层**：衬线体（思源宋体、Trajan）表古典与军工；无衬线表现代；基建用 Bender 这种"伪等距"字体加硬核感。中英混排当装饰。
- **层级手法**：背景模糊（acrylic）压非重点区域、vignette 提中心、卡片阴影做深度、局部失焦做前后关系。
- **画内界面**：主看板做成 PRTS 的全息投影，手机电量/信号/时间都被塞进浮窗并随陀螺仪移动——用 UI 本身讲世界观。

## 3. 调研三：我们自己的架构是什么

### 3.1 现状拆解

| 环节 | 我们的做法 | 代码位置 |
|---|---|---|
| 几何 | Blender 4.5 headless + Python `bmesh` **纯代码生成**，无手工建模、无雕刻、无高模烘焙 | `tools/blender_n5/*.py` |
| 贴图 | 3 张程序噪声（石材/土壤/叶片）+ 1 张叶图集；**法线与 PBR 图在运行时用 JS 生成** 512²×4 套 | `CourtyardBootstrap.ts: makeSurfaceTexture` |
| 材质 | 按物体名逐条覆盖颜色/粗糙度；无 trim sheet、无图集、无顶点混合 | `MAT_OVERRIDES` |
| 光照 | 1 主光（实时阴影 4096）+ 4 盏补光 + 手绘树影贴片；**无光照烘焙** | `setupLights()` |
| 角色 | Spine（930 KB：atlas+png+skel）→ RenderTexture → 世界面片 + Unlit | `harness_contract` |
| 导出 | GLB（关闭切线），70 MB，无压缩 | `export_glb` |
| 引擎 | Cocos Creator 3.x → web-desktop → puppeteer 截图 | `demo_n5s1` |
| 变体 | 环境变量切三套风格（O/C/R） | `THREE_STYLES.json` |

> **一处数据修正**：前版写"角色 78.5 万面"，是错的。`candidate_n5s1q/captures/q06_stats.json` 里 `scopes.CHAR001.tris = 785,540` 与 `CHAR002` 数值完全相同、且小于 `MAP001` 单独计数，是**关掉角色后的隔离渲染计数**，不是角色预算。项目里没有 78.5 万面的角色资产——角色就是 930 KB 的 Spine。**这一条从差距清单里删掉，换成"角色侧已经达标"。**

### 3.2 这套架构的真实优劣

**优势（真的）**
- 改一个参数重出整个场景，三套风格 8 分钟跑完——手工建模做不到的迭代速度；
- 无外部资产依赖，许可干净；
- 结构可审计：每个缺陷能追到具体生成函数。

**劣势（结构性的）**
- **几何即细节**：没有贴图承担细节，信息全堆在三角面 → 905k 面 / 70 MB；
- **材质不共享**：36 材质、540 draw call，方舟同类场景是个位数；
- **贴图运行时生成**：启动多花时间，512² 程序法线在掠射角走样——之前修的砖面白点就是这个根因；
- **无烘焙**：手机上一盏实时阴影 + 4 盏实时光是很贵的组合，方舟只留一盏；
- **无 LOD**：远景树和近景树同一套面数。

## 4. 横向对比

| 维度 | **明日方舟（本体）** | 我方（程序化 demo） | 主流小游戏 3D | CC0 kit 工作流 |
|---|---|---|---|---|
| 组合方式 | 3D 场景 + 2D Spine 单位 | **3D 场景 + 2D Spine 单位（同构）** | 3D 场景 + 3D 或 2D 角色 | 全 3D |
| 几何来源 | 手工雕刻，**块面化**，官方称"面数相对较高" | Python/bmesh 代码生成 | 手工低模 / 模块化 kit | 现成 kit |
| 单场景面数 | 未公开；靠静态合批而非低面数取胜 | **905k** | 5–15 万 | 2–10 万 |
| 承载细节的介质 | **贴图 + 烘焙光照**（高度图、风格化手绘） | **三角面** | 贴图 + 烘焙 | 贴图 |
| 法线/细节图 | 场景 shader 内置**高度图** | **运行时生成 512² 程序法线** | 离线烘焙 | 自带 |
| 光照 | **烘 Lightmap + Shadowmap 两张，运行时仅 1 盏动态光** | 实时阴影 + 4 盏补光，**零烘焙** | 烘焙 + 1 主光 | 烘焙 |
| **Draw call** | **个位数**（静态合批） | **540** | 30–80 | 5–15 |
| 材质策略 | 场景合批 + 主题 tint | 36 个材质，逐物体覆盖 | trim sheet + 图集 + ASTC | 自带图集 |
| 角色 | Spine + Unlit + 正反两套 + 纸片翻转 | Spine + Unlit（**同构，但只有单面**） | 2D 或 5k–2 万面 | 无 |
| 3D/2D 融合 | **主题 tint + color grading + Bloom + Vignette** | 无统一 tint，靠逐物体改色 | 同引擎即可 | — |
| 空间关系 | 相机 60°/角色 30°，**顶点着色器改深度** | 角色直接站在 3D 地面（未见穿模问题） | 标准 | — |
| 关卡生产方式 | **二维数组 JSON + tile prefab** | 程序化生成 + 手调参数 | 手工摆放 | 拼装 |
| UI | 灰度 90% + 单一强调色、磁带盒未来主义、画内界面 | 常规 HUD | 常规 | — |
| 包体 | 手游级（不适用 30 MB） | **70 MB**（上限 30 MB） | 8–25 MB | 取决于裁剪 |
| 迭代速度 | 慢（人力密集） | **快**（参数化重出） | 中 | 快 |

### 4.1 关键结论

1. **"3D 场景 + 2D 角色"这个组合我们选对了。** 这是二游的标准解，方舟、少前、碧蓝都是这个路子。角色侧我们甚至已经和方舟完全同构（Spine → RenderTexture → 面片 + Unlit）。
2. **差距不在面数，在"面数能不能被合批和烘焙消化掉"。** 方舟官方说得很清楚：他们**不追求低面数**，靠静态合批把 draw call 压到个位数、靠烘焙把光照成本降到一盏灯。我们反过来——面数偏高，还每块砖自己一个材质、每盏灯都实时算。
3. **所以"把 905k 砍到 5 万"不是正确答案。** 正确顺序是：先让它**能合批**（材质收敛 + 图集 + 静态标记）、**能烘焙**（lightmap 替代 4 盏补光）、**能压缩**（属性手术）。做完这三件，905k 面在手机上未必不能跑，但 540 draws 一定跑不好。
4. **我们缺的不是 NPR 层。** 前版把"缺 PBR+NPR 混合"当结论，那是照《终末地》说的。方舟本体是**纯 PBR 场景 + Unlit 2D 单位 + 后处理调色**——它的"手绘感"来自**风格化贴图绘制和块面化造型**，不是来自 NPR shader。我们要补的是"用贴图而不是用面数画细节"。
5. **我们的程序化能力是被需要的，但位置错了。** 该用在"散布、变体、植被、关卡生成"，不该用在"每一块砖自己一套几何"。方舟用二维数组生成关卡，我们用代码生成每一块石板的顶点——同样是"程序化"，一个在关卡层，一个在顶点层。

### 4.2 一个反直觉的对照

方舟的场景"面数相对较高"，我们的场景"面数很高"，但：

- 他们整场景 **个位数 draw call**，我们 **540**；
- 他们 **2 张烘焙图 + 1 盏灯**，我们 **实时阴影 + 4 盏灯 + 运行时生成法线**。

也就是说，即便面数打平，我们的渲染成本还是高一个量级。**这才是"不像主流"的地方。**

## 5. 实测：70 MB 到底花在哪（这条决定了路线顺序）

直接解析 `candidate_n5s1q/source/MAP001_courtyard.glb` 的二进制块，按语义统计字节：

| 属性 | 大小 | 占比 | 说明 |
|---|---:|---:|---|
| POSITION | 19.0 MB | 28% | float32 ×3 |
| NORMAL | 19.0 MB | 28% | float32 ×3，**和顶点数一样多** |
| TEXCOORD_0 | 12.6 MB | 18% | float32 ×2 |
| COLOR_0 | 12.6 MB | 18% | **大部分网格已不用**（叶片/草/硬表面都关了顶点色） |
| INDICES | 5.4 MB | 8% | u32 |
| 合计 | **68.9 MB** | 100% | 169 meshes / 36 materials |

**关键推论：这个文件的大小几乎和美术内容无关，全是顶点属性格式。**

| 处理 | 省下 | 画面影响 |
|---|---:|---|
| 导出时不带 COLOR_0 | −12.6 MB | 无（引擎已不用） |
| POSITION float32 → int16（量化） | −9.5 MB | 肉眼无感 |
| NORMAL float32 → int8 | −14.3 MB | 高光略软 |
| TEXCOORD float32 → uint16 | −6.3 MB | 无感（UV 在 0–1） |
| INDICES u32 → u16 | −2.7 MB | 无 |
| 以上合计 | **−45.4 MB → 23.9 MB** | 无结构性变化 |
| 再叠 MeshOpt（`gltfpack`） | 再 −25~35% | → **约 16–18 MB** |

**不改美术、不重建资产，70 MB 可以压到 17 MB 上下**——引擎 5.1 MB + 地图 17 MB < 30 MB，还剩 8 MB 给角色和 UI。

## 7. 方案：三条路线（按投入从小到大，顺序已改）

### 路线 0 · 属性手术（先做这个）

**做什么**：导出时去掉 COLOR_0；POSITION/NORMAL/UV 量化；索引降到 u16；过一遍 `gltfpack`。

**代价**：半天到 1 天。**不改美术、不改布局。**
**预期**：70 MB → 16–18 MB（第 5 节实测推算）。
**风险**：Cocos 对 quantized attribute 的支持要实测；若 `KHR_mesh_quantization` 不吃，退化到"只删 COLOR_0 + MeshOpt"也能到 30 MB 左右。
**验收**：同机位截图逐像素对比 ΔE 平均 < 2；包体 ≤ 20 MB。

### 路线 A′ · 方舟式收敛（替代前版的"模块化重构"）

前版这条是照《终末地》写的（trim sheet + NPR），现在按方舟的真实方案重写。**核心不是换资产，是换渲染组织方式。**

**做什么**（按性价比排序）

1. **材质收敛 + 静态合批**：36 个材质压到 8 个以内。**优先动 10 个 leaf 材质（占 242/447 prims）和 2 个草材质（70 prims）**——合并成"1 个叶图集材质 + 1 个草图集材质"，颜色走 `COLOR_0`（导出为 ubyte normalized，避开 uint16 被当 float 读的发白问题）。单这一步预期 447 → 约 150 prims。铺装**不用动**，它只有 1,800 面。
2. **烘焙替代实时光照**：场景烤 Lightmap + Shadowmap，运行时只留 1 盏动态光，删掉 4 盏补光。视觉上更接近方舟那种"细腻但便宜"的阴影。**只做单套风格，所以只烤一遍。**
3. **贴图从"运行时生成"改"构建期生成一次写盘"**：顺手消掉掠射角走样，启动也快。
4. **几何从"逐块石板"改"索引网格 + tile 表"**：参照方舟的 `map[i][j] → tiles[idx]` 结构（详见 `ARKNIGHTS_MAP_DECOMPILED.md`）。注意这一项**不是为了省面**（铺装本来就轻），而是为了**可编辑性和石板缝一致性**——缝由网格边界给出，不再逐块随机内缩。
5. **植被保留程序化**（这是我们的优势），但改成**图集卡片 + GPU 实例 + 2 级 LOD**。
6. **主题 tint + 后处理**：给场景和角色一套统一 tint，加 color grading / vignette。这是方舟把 3D 和 2D 融在一起的原手段，我们一条都没有。

**代价**：3–4 个工作日（第 1、2 项占一半）。
**风险**：烘焙会锁死光照，三套风格（O/C/R）要各烤一遍，或改成运行时可换 tint + 保守烘焙。
**验收**：整包 ≤ 25 MB；draws ≤ 120；同屏 ≤ 400k tri；1080p 中端机 30 fps。

### 路线 C · 2.5D 兜底

**做什么**：静态图那条线（Blender Cycles 出 2K 背景板 + 分层深度）+ 角色/道具用 3D。背景一张图 1–2 MB。
**代价**：2 天，可直接复用 `art/static_map`。
**风险**：不能自由转视角。
**适合**：如果玩法是固定机位的点击/收集，这条最省。

### 推荐顺序

**路线 0 → 路线 A′（重点做 1、2 两项）→ 视结果决定要不要 C。**

理由：路线 0 可能直接把包体压进线内；路线 A′ 的前两项（合批 + 烘焙）是**方舟方案的核心，也是最便宜的部分**，做完就能看出"程序化几何 + 合批烘焙"到底成不成立。只有当前两项做完观感还是"引擎预览感"，才需要动第 4 项（重做模块 + 图集）。

**不建议**：直接照《终末地》上 PBR+NPR 混合、或直接把 905k 砍到 5 万。前者不对症（方舟本体就是纯 PBR），后者砍完观感会塌，而包体问题其实靠属性量化就能解决。

## 8. 立刻可做的 5 件事（不改架构）

1. **导出关闭 COLOR_0**：`export_glb` 加 `export_vertex_color='NONE'`，直接省 12.6 MB。
2. **跑一次量化**：装 `gltfpack`，对现有 GLB 跑 `-cc`，量真实压缩率与画面损失。
3. **材质合并 + 静态标记**：36 → 8 个材质，看 draws 从 540 掉到多少。**这是验证方舟路线是否可行的最小实验。**
4. **关掉运行时法线生成**：四套 512² 程序贴图改构建期生成一次写盘。
5. **植被 LOD**：远景树线换 3 tri 卡片，通常砍掉 30% 面数。
