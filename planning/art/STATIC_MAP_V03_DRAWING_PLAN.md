## 0. 结论先说

1. **画法不是"再建一个 3D 场景"，是"填三张表 + 分六层出图"。** 三张表来自方舟：地面索引网格、摆件挂点表、相机与光照参数。填完表，生成器出场景，六层分别渲染，最后合成。
2. **角色和 UI 不进 Blender 的 3D 场景。** 角色走 Spine 首帧贴片（世界空间 billboard + 接触阴影），UI 走项目已有的 `deco_*` 与 `icons/*`，在 2D 合成阶段叠上去。**好处：改 UI 不用重渲染，改一句文案不花 41 秒。**
3. **六层按 z 深度分，不按语义分**，这样以后想转 2.5D 视差，直接拿层做位移即可。
4. **构图差距比机位更本质**：实测"受光暖铺装"（`L>145 且 R−B>28`）的行覆盖率——参考有 **20% 高度**超过 50%（y 52–72%，峰值 79%），v02 **一条行都没有**（峰值 41%，且出现在画面顶部 y16%）。参考是一条亮带、四边压满；v02 是一整片不暖的空广场，**视觉重心整个反了**。这条不修，调多少次机位都还是"空"。
5. **观感的四个硬差距全部量化了**（第 1.3 节）：树冠太灰太亮、铺装偏暗不够暖、远景冷暖关系反了、金属明暗方向反了。这四条是"像不像参考"的主体，比加几何收益大得多。
6. **验收口径要修正**：v02 的 `REVIEW.md` 写"总分 ≥90"，但项目 `rubric.json` 是 **pass_total 85**、core 维 ≥3、**四张卡（ENV/CHAR/UI/MIX）各自通过**。以 rubric 为准，否则会把自己卡死在一个比项目更严的标准上。

### 1.2b 构图第一原则：四边压满，只留一条亮带

不用"开放铺装"这种含糊说法，用像素级判据：**受光暖铺装 = `L > 145 且 R−B > 28`**（"暖色受光石材"的特征），统计每一行里这类像素的占比。

| | 峰值 | 峰值位置 | 占比 >50% 的行 |
|---|---:|---|---|
| 参考 t084s | **79%** | y 62% | **y 52–72%，共 20% 高度** |
| v02 | 41% | **y 16%（画面顶部）** | **无，一行都没有** |

**两个硬结论：**

1. **v02 的广场在像素判定上"不算暖铺装"**——它 L 够（163）但 R−B 只有 26，卡在 28 阈值下面。整张图没有一条行超过 50%。
2. **v02 最亮的暖区在画面顶部，参考在中下部**——视觉重心位置反了。这比"某个颜色不对"严重，它决定眼睛先看哪。

参考图左侧被树+叉车压住、右侧被草墙+圆筒压住、上边被树冠+远景压住、下边被台阶压住，中间只留一条 20% 高的亮带做视觉中心。

执行口径：**任何一版渲染，受光暖铺装占比 >50% 的行必须落在 15–25% 高度之间，且峰值位置在 y 55–70%。**

### 1.3 材质分离：四个量化差距（这是主要工作量）

> **口径声明**：本表全部为 **HSV**，`sat = (max−min)/max`，`L = 0.2126R+0.7152G+0.0722B`。不要与 HSL 的 S 混用（同色差约 9 个点）。

| 材质区 | 参考 | v02 | 差 |
|---|---|---|---|
| **树冠** | `#67432f` L73 sat**55%** R−B56 | `#7e7264` L116 sat**20%** R−B26 | **亮 43、饱和度低 35** |
| **铺装（受光）** | `#c7af9a` L179 sat22% R−B45 | `#aea293` L163 sat15% R−B26 | 暗 16、饱和低 7、色温低 19 |
| **远景带** | `#877e75` L127 sat14% R−B+18 | `#647883` L117 sat24% **R−B−31** | **参考无冷色簇，冷色像素仅 2.8%；v02 有 12.3%** |
| **金属** | `#b6a69a` L169 sat15% | `#736556` L103 sat25% | 暗 66，且方向反了（参考金属是**亮而灰**） |
| 草池 | `#89684c` L109 sat44% | `#9a856c` L136 sat30% | 亮 27、饱和低 14 |

**四条结论：**

1. **树冠不是"太深"，是"太灰、太亮"。** 参考 sat 55% / L73，v02 sat 20% / L116。饱和度差 35 个点，所以看着像烧焦的灌木；参考是**深而艳**，不是深而灰。
2. **铺装差的是"暖"不是"亮"**（只差 16），色温差 19。所以调法不是提亮，是**把 R−B 从 26 拉到 45**。
3. **远景冷暖反了**：v02 是 `B>R` 的冷蓝带（sat 24%），参考是 `R−B+18` 的**暖灰**（sat 14%）。这一条不修，"硬色带"永远在。
4. **金属要反过来做**：参考是高明度（L169）低饱和（sat15%）——因为反光；v02 做成 L103 sat25% 的暗脏色。改成**提亮 + 去饱和**。

## 2. 数据结构：借方舟的三张表

方舟的关卡是"二维索引网格 + tile 定义表 + 相机参数"（见 `ARKNIGHTS_MAP_DECOMPILED.md`）。我们照这个思路，把"画一张图"拆成"填三张表"。

### 2.1 表一 · 地面索引网格 + surface 表

**1 m 索引网格，48 列 × 28 行**（48 m × 28 m）；**石板模块占 2×2 格 = 2 m**，保持参考图"大板"的尺度。台阶不走网格，走参数化踏步（见 2.1b）。

```jsonc
"grid": { "cell": 1.0, "cols": 48, "rows": 28, "slab_module": 2, "origin": [0, 0] },

"surfaces": [                       // 每格一个 surfaceKey，不是坐标
  ["wall","wall","paving","paving","paving","paving", ...],
  ["wall","paving","paving","paving","paving","paving", ...],
  ...
],
"surfaceTypes": {
  "paving":      { "mesh":"tile_slab_2x2",  "uvBlock":[0,0], "height":0.00, "edge":"joint"  },
  "paving_edge": { "mesh":"tile_edge_1x2",  "uvBlock":[1,0], "height":0.00, "edge":"bevel"  },
  "paving_patch":{ "mesh":"tile_patch_2x2", "uvBlock":[2,0], "height":0.00, "edge":"joint"  },
  "soil":        { "mesh":"tile_soil_2x2",  "uvBlock":[4,0], "height":0.15, "edge":"curb"   },
  "wall":        { "mesh":"tile_wall_2x2",  "uvBlock":[5,0], "height":0.60, "edge":"cap"    }
}
```

**为什么这么画**：石板缝由**网格边界**给出，不再逐块随机内缩——上一轮折腾很久的"缝宽不齐、砖面白点"，根因就是每块石板是独立物体。网格化之后缝宽天然恒定。

**为什么 1 m 而不是 2 m**：边板、修补板、路缘需要 1 m 的定位精度；而石板本体按 2×2 格合成 2 m，尺度不变。**精度给到索引，尺度留给模块。**

### 2.1b 台阶：参数化，不网格化

```jsonc
"stairs": [
  { "run": [[15,0],[45,0]], "dir":[0,1], "steps":9,
    "tread_m":0.52, "riser_m":0.155, "width_m":9.0,
    "nosing":"bevel", "side_wall":"left|right" }
]
```

台阶是重复构件，用"级数 + 踏步深 + 踢面高"生成，比铺 48 个格子更省且更好调。参考图 8–10 级，取 9 级。

### 2.2 表二 · 摆件挂点表

```jsonc
"props": [
  { "key":"tree_maple_a",    "at":[6,4],   "rotY":32, "scale":1.15, "layer":"L1" },
  { "key":"planter_cyl",     "at":[13,3],  "rotY":0,  "scale":1.0,  "layer":"L1", "variant":2 },

  { "key":"grass_wall",      "at":[22,6],  "rotY":90, "scale":1.0,  "layer":"L1" },  // #16 右侧大草墙
  { "key":"tank_cyl_double","at":[17,7],  "rotY":0,  "scale":1.0,  "layer":"L1" },  // #17 中右圆筒罐
```

## 3. 分层出图规格（六层，按 z 深度分）

| 层 | 深度 | 内容 | 雾化 | 输出 |
|---|---|---|---|---|
| **L0 远景** | 30–60 m | 水岸、岸带、树/建筑剪影 | **强**（fog 18→46 m 全作用） | PNG + alpha |
| **L1 中景** | 8–30 m | 平台、设施、圆筒草池、主树、格栅门 | 弱 | PNG + alpha |
| **L2 铺装** | 2–12 m | 广场石板、台阶、两侧挡墙 | 无 | PNG + alpha |
| **L2.5 前景遮挡** | 1–3 m | 栏杆、彩旗、近处草丛 | 无 | PNG + alpha |
| **L3 角色** | 挂点 | Spine 首帧贴片 + 接触阴影 + 选中框 | 无 | PNG + alpha |
| **L4 UI** | 屏幕空间 | 纸张面板、涂鸦、图标、提示文字 | — | 矢量/PNG |

**为什么按 z 分而不是按语义分**：以后要做 2.5D 视差，只需要给 L0/L1/L2 三层不同的水平位移系数（例如 L0 ×0.3、L1 ×0.6、L2 ×1.0），立刻有纵深；按语义分（"树层""设施层"）就做不到。

#### 出图方式（2026-10-28 修正）

**不要"每层单独渲染一次"。** 每层只显示该层物体去渲，各层的 GI 互反射不同，六张合起来会比一次渲染的整图更平、更冷、更碎，"留一张合并图作基准"也救不回来。

正确做法：

1. **只渲一次 beauty**（全场景、全光照、1920×1078）；
2. 同时输出 **Cryptomatte / Object Index** 遮罩（按 L0/L1/L2/L2.5/L3/L4 分组）；
3. 在合成阶段**按遮罩把这一张 beauty 拆成六层** —— 六层像素来自同一次光照计算，合回去逐像素等于原图。

两个必须配套的约束：

| 约束 | 值 | 原因 |
|---|---|---|
| **overscan** | 110–120% | 视差时层会横向位移，不预留就露边；方案早期版本漏了这条 |
| **位移上限** | L0 ≤3%、L1 ≤6%、L2 ≤10% | 超过就会露洞（洞要靠补绘） |

日常迭代仍用 960×539 预览（约 12 秒/版）；正式出图一次 beauty（约 41 秒）+ 一次 Cryptomatte 输出。

### 4.3 合成顺序

```
L0 远景 → L1 中景 → L2 铺装 → L2.5 前景遮挡 → 角色 → 接触阴影 → 选中框 → UI → 后处理
```

后处理里只做三件事：**color grading（统一暖调）、vignette（压四角）、轻 bloom（只给远景和草尖）**。这三样是方舟把 3D 场景和 2D 单位揉在一起的原手段。

### 6.1 自查指标的三个补充（2026-10-28）

光靠"6×4 亮度均值"会被钻空子——在顶部塞一块暗物就能把顶行压下来，画面却完全不像。所以每轮必须同时过三条：

| 指标 | 做法 | 参考值 | 判定 |
|---|---|---|---|
| **每格标准差** | 6×4 每格算亮度标准差 | 待首轮实测标定 | 与参考同格差 < 25% |
| **每格边缘密度** | Sobel 梯度二值化后的边缘像素占比 | 待标定 | 与参考同格差 < 30% |
| **受光暖铺装行覆盖率** | `L>145 且 R−B>28` 逐行统计 | >50% 的行占 20% 高度，峰值 y62% | 落在 15–25% 高度，峰值 y55–70% |

前两条防"用色块骗均值"，第三条防"地面是亮的但不是暖石材"。

### 6.2 一致性闸门（最高优先级，一次设定全局生效）

上面 6.1 的三条都是"局部"指标。**真正保证美术效果一致的是四个全局机制**，详见 `ART_CONSISTENCY_MECHANISM.md`：

| 层 | 机制 | 参考值 | v02 | 判据 |
|---|---|---|---|---|
| **L1** | **一条全局色调曲线**（view transform 前置，所有渲染共用） | p50 **102** / p90 **194** / p99 **211** / >180 占 **20.1%** | 156 / 176 / 184 / **4.0%** | 六锚点各 ±10% 内 |
| **L2** | **单一色相轴**：材质只写明度+饱和度，色相由 sun/sky 注入 | 冷色像素 **2.8%**（无冷色簇） | **12.3%** | 冷色像素 ≤3% |
| **L3** | **色阶分档**：六档各有货，无单档独大 | 六档 4.6/25.8/23.6/12.2/13.6/20.1，最大簇 **20.2%** | 3.3/5.7/6.2/25.8/**55.0**/4.0，最大簇 **52.8%** | 每档在区间内，最大簇 ≤25% |
| **L4** | **细节频率口径**：同深度的 texel 密度与几何细节尺度一致 | 四象限边缘密度离散度 15.1% | 24.9% | ≤60%（软指标，先观察） |

**已经工程化**：

```bash
node tools/art/consistency_check.js <待检图> [--json out.json]
```

- 色彩来源统一到 `planning/art/style.json`（16 个命名 token），**代码里不出现字面 hex**
- 自检过：参考图 13/13 全通过（退出码 0）；v02 **12/13 不通过**（退出码 1）

**这条闸门的意义**：每改一版一条命令就知道一致性有没有退步，不用等评审。而且它对新加的物件自动生效——因为约束的是"所有像素过同一条变换"，不是"每个物件单独调色"。
