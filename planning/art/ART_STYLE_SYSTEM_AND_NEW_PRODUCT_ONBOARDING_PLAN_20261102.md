# 项目美术风格系统与新产品接入方案

日期：2026-11-02  
修订：r2，已修正预览快照、知识状态、前置小样、返修回路、增量审计及运行隔离契约。  
状态：**方案提案，未作为现行制作标准启用；不创建新产品、不制作图像。**  
目的：让新的地图、场景或美术产品接入同一项目后，能够继承明确的项目风格约束，同时保留该产品自己的参考、主题和内容，不因复用 P1 方案而画成同一张秋日地图。

## 项目必读入口设计（其他模型第一站）

每个开发任务开头都应有一个短小、权威的 `START_HERE.md`，作为“项目必读”和目录路由。它不复制所有规范，而是告诉执行模型：**先读什么、根据什么选业务知识、接下来读哪份工作单、哪些文件是历史或不适用的**。

### 根入口的职责

根目录 `START_HERE.md` 应成为**跨业务的项目入口**，建议只保留以下内容：

1. 当前项目范围和任务类型选择方式。
2. 必读顺序与每份文件解决的问题。
3. 通用开发层入口，以及按 `business_id` 读取业务包的规则。
4. 当前需求的 Brief、方案、待确认问题、测试计划和工作单路径。
5. 规则冲突优先级、过期/归档文档识别方式、禁止误读的业务包。
6. 开工时需输出的知识读取摘要；路由工具实现后由 `RESOLVED_KNOWLEDGE.json` 自动记录路径、版本和 SHA。

根入口不应内嵌 P1 秋日画面细节、评分数字或独立评审要求。P1 专属入口应作为 `business/p1_autumn_static/START_HERE.md` 或 P1 工作单保留；新业务各有自己的业务入口。这样新地图模型先读同一份项目目录，再只进入本次业务包。

### 知识与流程文档清理审计（迁移前必做）

建立通用目录或业务包之前，先审计本次将启用的知识、规范、工作流、模板、skill、Hook/Gate、Lessons 及其引用。不能只把旧资料复制进新目录；必须识别重复、过时、冲突、范围错误和缺少证据的内容，并给每条规则确定唯一归属与当前状态。此审计是迁移前置步骤，不代表本提案已经执行了文件清理。

审计分两种：首次迁移建立全库文件索引，但逐条审计优先覆盖活动入口、本次选中包及其依赖；未被引用的历史文件只登记状态，后续分批整理。日常接入仅审计本次加载集合中的新增/变更文件、变更规则和反向引用；已审计且 SHA、适用范围、用户要求及依赖均未变化的结论可复用。只有影响本次任务的未决冲突才阻塞该任务；无关历史清理不阻塞制作。

审计至少覆盖：根 `AGENTS.md`、`START_HERE.md`、`MODEL_EXECUTION_GUIDE.md`、`knowledge/README.md`、`STANDARDS.md`、`RECIPES.md`、`REUSABLE_MAP_ART_PIPELINE.md`、`LESSONS.md`/案例库、P1 工作流/视觉标准/活动工作单、项目 skills、Hook/Gate 与归档索引；同时搜索旧阈值、旧参考、旧制作边界及已撤销要求，检查它们是否仍被活动入口、脚本或链接引用。

| 审计分类 | 识别方式 | 必须采取的处理 |
|---|---|---|
| 完全重复 | 同一规则、阈值或步骤在多个文件重复出现，且没有各自独立的用途 | 选定一个权威来源；其他文件改为短摘要/链接，删除重复正文前先检查脚本、入口和历史引用 |
| 部分重叠 | 不同文件描述同一流程但阶段、字段或措辞不一致 | 对照当前实际执行链逐项合并；保留各层真正不同的内容，明确哪个文件负责规则、哪个负责操作细节 |
| 过时/已被覆盖 | 旧目标、旧分数、旧参考、旧范围或旧流程被后续明确决定替换 | 标 `superseded`/`deprecated`，注明替代文件、日期和原因；从必读入口与活动路由移除，历史追溯需要时保留 |
| 规则冲突 | 同一适用范围内同时要求相反行为，或活动文档与用户最新决定相反 | 按第 5 节优先级裁决并记录 `conflict → decision → source`；无法确定权威来源时标为 `blocking`，不得两套都加载 |
| 范围泄漏 | P1 秋日参数、零植被、85 分门槛等被写进通用规则，或通用规则被错误当作 P1 专项细节 | 拆分到正确层级；通用入口只链接业务规则，业务包不得改写通用 Harness 生命周期 |
| 未验证/证据不足 | 研究推论、单次试验或模型自评被表述为已验证事实/可复用最佳实践 | 方法成熟度退回 `observed/proposed`；未知事实写 `unknown` 并加 `needs_evidence` 标记；补证后才升级，未经批准的规范保持 draft |
| 孤儿/失效引用 | 已无活动任务使用的文档、技能、路径、工具指令或互相断开的链接 | 查清是否仍被代码/Hook/入口依赖；修复引用，或标历史归档并从当前路由解除 |

审计清单建议为 `KNOWLEDGE_AUDIT.json`，每条记录至少含 `path`、`sha256`、`scope`、`lifecycle`、`maturity`、`rule_ids`、`duplicate_of`、`conflicts_with`、`canonical_source`、`decision`、`replacement_or_archive_path`、`evidence` 和 `references_updated`。状态字段按第 1 节契约分开；一份文件可含多个状态不同的条款，审计应细到规则/章节，不能只给整份文档贴一个状态。

清理顺序固定为：**盘点与哈希 → 逐条识别 → 确认权威来源及适用范围 → 合并/拆分/修正 → 更新入口和反向链接 → 搜索残留旧规则 → 验证路由与脚本引用 → 保留审计记录**。不静默覆盖历史、不因“看起来重复”直接删除文件；归档前先检查引用与可复现证据，删除动作必须另有明确授权和备份策略。清理完成的验收条件是：每条活动规则只有一个权威正文；所有冲突有书面裁决；活动入口不再指向被废止文件；各业务包没有串入其他业务的规则；仍被保留的历史材料均不可被误识别为当前指令。

本项目已知的审计样例包括：`MODEL_EXECUTION_GUIDE.md` 的“双独立盲审”与当前“不要求独立终审”不一致，应修订或标历史；旧文档中被后续决定撤销的植被制作要求不得进入 P1 当前包；P1 的 85 分/零植被等限制不能成为新业务的通用门槛；`ART_DOCUMENTATION_ARCHIVE_INDEX_20261029.md` 已有权威文件和历史文件清理规则，应纳入新目录而非再造一份重复归档表。以上是本方案列出的待处理项，不代表这些文件已在本轮被修改。

### 建议的读取顺序

入口要区分**每轮必读**和**按需求/阶段读取**，不能要求模型在设计阶段读取尚未生成的测试或开发确认记录。

| 顺序 | 读取内容 | 规则 |
|---|---|---|
| 1 | `AGENTS.md` 的项目通用约束、根 `START_HERE.md` | 每轮必读；两者只保留真正跨业务适用的规则 |
| 2 | 用户本轮需求；已有 `REQUIREMENTS_BRIEF` 或活动任务指针 | 判断产品类型、业务 ID、工作阶段；无 brief 时先执行 N0，不先猜业务包；若知识审计标出本任务规则为 `blocking`，先解决冲突 |
| 3 | `knowledge/README.md`、`common/dev_core`、与交付类型相符的 `common/methods/<type>` | 读取通用开发核心；只读取本任务需要的方法模块，不要求所有产品类型通读地图制作流程 |
| 4 | 已选业务包入口、Profile、参考/评分标准，以及 manifest 指定的专项 skill（需要时） | 按 `business_id` 加载；混合业务只加载 Brief 明确列出的模块，不加载其他业务的美术指导 skill |
| 5 | 当前阶段已有的工作产物 | 需求阶段读问题单；设计后读方案/预览/测试计划；开发阶段读已确认方案、用例和工作单；未生成的阶段文件不应被要求必读 |

只读**被选中、状态有效且当前阶段需要**的文件。通用索引可以浏览，不能因此把所有业务文档全部载入上下文。历史、归档、`deprecated`、未选业务包只在追溯或明确研究时读取；审计未完成或权威来源不明的规则不能自动进入活动包。

### 当前入口的迁移注意项

现有根目录 `START_HERE.md` 实际是 P1 秋日静态地图专用入口，`AGENTS.md` 也含 P1 专属硬约束；两者都不能原样当成跨产品通用规范。推广前应把真正通用约束留在根入口，把 P1 规则收进 P1 业务入口。当前 `MODEL_EXECUTION_GUIDE.md` 的“两个独立盲审”要求与最新 P1 规则及用户已确认的“无需其他模型独立终审”冲突；在列为通用必读前，应将其标为历史/修订为通用规则，并把有效的 P1 约束以当前工作流和 P1 业务入口为准。**本方案只记录修订要求，不在本轮改写这些入口文件。**

## 一页结论

- **知识分两类：** `common` 负责通用开发方法；`business/<id>` 负责某类产品的专属目标和约束。秋日特征和 P1 绘制方法已有多份资料记录但尚未收成完整业务包；秋日是 `p1_autumn_static`，不是通用风格规则。
- **迁移前先做知识清理审计：**逐条识别重复、过时、冲突、范围泄漏、未验证和失效引用；建立唯一权威来源，修正活动入口，历史资料标记状态后保留，禁止静默删除或把旧规则误装进新业务包。
- **模型先看项目入口：**根 `START_HERE.md` 先给通用规则和知识目录，再按需求路由到一个业务入口；不把 P1 专用规则作为新产品的默认必读内容。
- **每轮按需加载：**先读通用执行约束，再按需求分类选业务包；将本轮读取的文件、SHA 和覆盖决定写入 `RESOLVED_KNOWLEDGE.json`，供 Harness preflight 核对。没有对应业务包时用新 Brief 初始化，不借用秋日画面答案。
- **先分析、设计和测，再制作：**输出需求追踪与待确认问题；方案必须附符合交付类型的低保真预览（地图灰模、UI wireframe、角色/道具轮廓板等）；测试用例从需求追踪生成；实际开发者确认方案及测试可执行后，才进入完整制作。
- **Harness 负责闭环：**锁定本轮约束 → 选择知识包 → 记录候选/证据 → 运行检查 → 失败回传修复 → 达标后交付和沉淀经验。
- **当前真实状态：**项目已有 P1 专用的会话 Hook 和机械质量 Gate；它能阻止证据/门槛未过的 P1 会话正常结束，并把修复项交回同一会话。跨业务知识路由、通用 Harness Spec、Blender 自动执行和自动视觉判断仍未实现。
- 本方案仅设计知识结构和接入办法；不代表已完成文件迁移、已批准全局美术基线或已建成通用自动化 Harness。

### 当前缺口

**知识库存在，但“项目通用风格系统”尚未正式定义。** 现有资料能告诉新模型一些工作方法和用户偏好，却没有单一、明确、已批准的文件回答：

1. 哪些是所有产品都必须遵守的风格不变量？
2. 哪些特征只属于 P1 秋日静态地图？
3. 新需求如何声明参考图、主题、平台、目标画面和禁止项？
4. 新模型从哪份 brief 读起、何时可以开始批量制作？
5. 如何评估“与项目风格一致”，而不是要求新产品复制 P1 的秋色、构图或设备？
6. 新产品成功后，怎样把经验加入知识库而不把单次试验误升为通用规则？

### 知识库应采用“通用开发层 + 业务知识层”

知识库不能按“所有文档都读一遍”来工作。主知识库只有两类：**通用知识 `common`** 与 **按需选择的业务知识 `business/<id>`**。`common` 也分成“每轮必读的开发核心”和按交付类型选读的方法模块；通用美术基线是其中只对美术任务加载的可选模块。当前需求则是每轮生成的运行上下文，不是第三套共享知识库。

| 层 | 回答的问题 | 典型内容 | 加载规则 |
|---|---|---|---|
| 通用开发核心 `common/dev_core` | 如何管理任务、文件、证据和结束状态？ | Harness 生命周期、需求追踪、源/候选隔离、版本与哈希、日志、复现、知识维护边界 | 所有开发任务必读；仅包含跨业务硬规则 |
| 通用方法模块 `common/methods/<type>` | 这类交付通常怎样制作和验证？ | 地图灰模/构图/返修方法、角色/UI制作方法等 | 按 `deliverable_type` 选读；静态地图方法不强迫 UI/角色任务加载 |
| 通用美术基线 `common/art_base` | 哪些画面原则在本项目默认共用？ | 经用户确认的层级、可读性、逻辑摆放、细节密度、素材可编辑性等规则 | 仅对美术任务加载；当前候选条款须经确认后才可启用 |
| 业务知识 `business/<业务包>` | 本类产品具体要画成什么样、有什么专属约束？ | 主题参考、构图/色彩/材质目标、资产语义、业务参数、评分表、已验证案例和禁用项 | 由需求分类选中后加载；没有命中的业务包不得自行套用相似主题的视觉答案 |
| 当前需求上下文 `active_request` | 这一次具体交付什么、覆盖哪些旧规则？ | 本次 Brief、明确覆盖、交付边界、目标版本、运行平台和验收证据 | 每次任务新建的运行记录；不是可自动继承到其他产品的知识包 |

“秋日静态地图”是一个业务包（例如 `p1_autumn_static`），不是通用开发规范。它的秋日配色、固定参考、零植被和构图参数只能在该包被显式选中时加载。通用开发层仍可用于其他地图；具体业务包不能反向改变 Harness 的通用规则。

### 按需求加载知识的确定性规则

知识条目采用三个独立字段，禁止把它们混进单一 `status`：

| 字段 | 值与含义 | 加载/使用规则 |
|---|---|---|
| `scope` | `common/dev_core`、`common/methods/<type>`、`common/art_base`、`business/<id>` | 决定适用范围；某业务成功不自动升级为通用 |
| `lifecycle` | `draft`、`active`、`superseded`、`deprecated`、`historical` | 决定当前是否生效；只有 `active` 规范可成为验收要求，启用依据写入 `activation_basis` |
| `maturity` | `not_applicable`、`proposed`、`observed`、`reproduced`、`reusable` | 决定经验可信程度；用户明确的产品要求用 `not_applicable`，不要求先用实验验证用户偏好 |

`needs_evidence` 是证据缺口标记，`unknown` 是尚未知晓的事实，不作为生命周期。未经批准的项目美术基线使用 `lifecycle=draft`；可研究但不能作为门槛。制作方法按以下方式启动：`proposed/observed` 可进入明确标记 `experiment` 的低成本小样；小样满足预先写明的业务用例后，记录证据并允许在本次业务扩产，可标 `reproduced`。`reusable` 只表示在声明范围内复测有效；升级为 common 的 `reusable` 还须至少两个不同业务包验证并记录反例。首次业务不必等待跨业务验证才能制作。一次试验通过不能自动修改评分标准，也不能把未批准的风格要求设为 `active`。

1. **先分类，再读业务资料。**从需求中提取 `deliverable_type`（静态地图/可行走地图/UI/道具等）、主 `business_id`、平台与交付范围；不确定时先建立 Brief 并标明待确认项，不猜业务包。manifest 只提供候选匹配，不应只靠关键词自动决定最终业务包。
2. **先加载通用开发层。**所有任务读取项目级通用指令、通用知识索引和适用于本任务类型的 Harness/制作流程；美术任务再加载已批准的 `art_base`。`AGENTS.md` 只有通用执行约束进入 `common`；若其中混有 P1 规则，必须先拆到 P1 业务包，不能因文件位于根目录就把它当成跨业务规范。
3. **只加载明确选中的业务包。**通常一个主业务包；仅当交付确实跨业务时，Brief 才可声明多个业务模块，并分别标明共享/隔离的约束。按 manifest 的 `required_docs` 读取必需资料，`optional_docs` 由范围决定；不可因为关键词相似自动混入其他业务包的参考图、色板、镜头或分数规则。
4. **将本次上下文锁定并留证。**生成 `RESOLVED_KNOWLEDGE.json`，记录 `business_id`、交付类型、已加载文件路径与 SHA、`scope/lifecycle/maturity`、`usage`（requirement/method/experiment）、继承/覆盖/不适用决定，以及未加载的相邻业务包。Harness preflight 只接受清单中明确启用的业务规则；试验方法不得变成验收要求。新规则版本需显式更新本次绑定并复核影响，不能静默替换。
5. **没有匹配包时走初始化。**只用通用层和用户当前 Brief；为新业务建立新包和小样，不复制秋日包或其他历史产品的视觉答案。通用方法可复用，但必须标明方法复用不代表风格复用。
6. **多业务混合时显式组合。**例如同一交付同时含地图和 UI，应在 Brief 声明主业务与辅助业务，以及共享/分离的验收项，冲突处写决策；不能让加载顺序隐式决定风格。

**路由示例：**“继续画 P1 秋日静态地图”加载通用开发层 + 已批准的项目美术基线（若已启用）+ `p1_autumn_static` 业务包；“做一张新的科幻工厂地图”加载通用开发层 + 已批准的项目美术基线（若已启用），再新建科幻工厂 Brief/Profile，不加载 P1 秋日色板、相机、零植被约束或评分表。若项目美术基线仍为 `lifecycle=draft`，只可作为待确认信息列出，不得作为强制验收规则。

业务 manifest 至少包含：`business_id`、适用交付类型/触发词、`lifecycle`、`activation_basis`、`required_docs`、`optional_docs`、排除包、该包的 `style_profile_id`、`skill_refs`、评分规范、Harness 检查集和版本。业务包升级时应形成新版本并记录 SHA，不能静默更换当前任务已锁定的规则。

## 2. 风格一致的定义

项目风格一致不是所有产品共用同一种配色、物件、镜头或地图布局。它由两层构成：

### A. 项目级风格不变量

以下是候选条款，当前不自动继承；只有被明确批准并标为 `lifecycle=active` 的条款，才在适用产品中默认继承。用户本次明确要求仍按需求 Brief 执行：

- 画面先保证主次明确、轮廓易读、物件有用途和结构逻辑。
- 优先使用较少、较大、可辨认的主体形体；避免无意义的碎物堆叠和细节噪声。
- 植被默认避免密集堆叠；是否完全移除应由具体产品 brief 决定。当前 P1 的“完全无植被”是地图专属规则，不能自动推广到所有产品。
- 材质、光色、轮廓和细节密度服务于同一套场景层级，避免每个物件各自一套画法。
- 生产素材应可追溯、可修改、可复现；不能把未经用户批准的 AI 直出图片当成最终可编辑源。若使用 AI 辅助构思，需标为参考/草案，最终产品资产应转成项目认可的可控素材。
- 对新主题的变化先做小样和风格对照，再扩大制作范围。

这些是基于现有用户偏好和工作经验提出的**候选项目级不变量**，需要用户确认后才能成为正式 Style Bible。当前仓库并没有一份已批准的跨产品完整 Style Bible。

### B. 产品/地图专属视觉变量

每个产品自己定义，不能从 P1 自动复制：

- 主题、时代、地域、情绪和主要故事语义。
- 该产品的视觉参考图、色彩角色、几何语言、材质和光照方案。
- 地形、建筑、植被策略、物件清单、地图拓扑、镜头和构图。
- 目标平台、最终分辨率、运行预算、画面安全区和交付格式。
- 该产品的评分维度、权重、硬门槛和可接受偏差。

**跨产品复用的是风格规则、资产制作习惯和验证方法；不复用 P1 秋日参考的答案。**

验收分开回答两个问题：**项目一致性**（仅评已批准的 common 美术基线）与**业务目标符合度**（对照当前业务参考和产品 Profile）。两者分项报告，不能用业务主题相似掩盖项目规范偏差，也不能因新产品配色/题材不同就判它“不像 P1”。没有批准的 common 美术基线时，只报告业务符合度，不设置虚构的全局一致性分数。

## 3. 新需求接入流程

新需求按 `N0–N8` 连续推进。**N0–N4 是批量制作前的需求/设计确认阶段**，允许为设计制作可编辑灰模、粗色光及代表小样；未解决的关键问题、未确认的方案或没有验证方法的要求，不得直接进入批量制作。N5 验证从设计快照派生的原型后，才扩展完整资产。

本方案统一以 `REQUIREMENTS_BRIEF.md` 保存本次需求，`SOLUTION_DESIGN.md` 保存设计，`test_cases.json` 保存用例，`DEV_FEASIBILITY_REVIEW.md` 保存开发确认。Brief 不另建同义副本。`OPEN_QUESTIONS.md` 只维护问题及决定指针，决定正文只保存在 `DECISION_LOG.md`。小任务可在同一文档中使用命名章节承载需求/问题/设计/确认，manifest 必须记录唯一定位；机器用例和运行绑定仍保持结构化文件，不能复制两套正文。

### 流程按变更影响裁剪

完整新业务、新参考/风格 Profile、交付类型变更或验收规则变更，走完整 N0–N8。已锁定业务包内的局部返修不重做整套分析：沿用原 `RESOLVED_KNOWLEDGE` 和需求基线，只重开受影响阶段/用例；若变更触及目标效果、画面布局、验收条件或预算，则重做对应 N2/N3 并重新做 N4 开发确认。任何改动都不能跳过 N7 的最终验收；不受改动影响且仍绑定同一产物 SHA 的证据可以复用。

### N0 · 需求分析模块

把自然语言需求变成有来源、可执行、可验收的要求，不能把“好看、像参考、丰富”等词原样当作验收标准。每项要求记录 `REQ-ID`、来源、优先级、适用业务、验收方法和证据。

分析至少覆盖：产品类型与用户目的、最终交付与明确不做项、平台/画幅/展示条件、视觉/结构/工具参考或“原创方向”声明、必须出现/禁止出现的内容、风格偏好、时间/性能/磁盘约束、评分目标、与既有知识的冲突。

待确认问题单必须列：`Q-ID`、问题、为什么影响结果、可选答案、推荐默认值、选错的返工影响、负责人（用户/开发者）和状态。区分 `blocking` 与 `non_blocking`：blocking 问题未答不能冻结设计；non-blocking 可采用标注过的默认假设。

**输出：** `REQUIREMENTS_BRIEF.md`、`REQUIREMENTS_TRACEABILITY.json`、`OPEN_QUESTIONS.md`。每条验收要求先在追踪矩阵中分配预期测试 ID；N3 生成正式用例后必须全部闭合，或说明为什么目前只能人工判断。

### N1 · 知识路由与参考资料归档

先加载通用开发层，再按 `deliverable_type` 和 `business_id` 选业务包；没有业务包时标记 `new_business_bootstrap`，不得默认读取 P1 秋日规则。参考按角色区分：

| 标记 | 含义 | 可以决定什么 |
|---|---|---|
| `visual_reference` | 画面、美术、材质、光色参考 | 风格和视觉验收 |
| `structural_reference` | 真实地图、布局、尺寸、路线、空间关系 | 几何/拓扑与内容组织 |
| `tooling_reference` | Blender、引擎、插件或制作流程资料 | 工具选型和技术操作 |

每项参考记录来源、日期、路径、SHA、用途、许可边界和可观察特征。没有视觉参考时，必须标明“原创方向”，不能从相邻业务包偷借画风；如新画风选择会显著改变成品，作为 blocking 问题提供有限选项供用户决定。Brief 中逐条标记业务规则 `inherit`、`override` 或 `not_applicable`；结构资料不能冒充美术参考，工具文档不能冒充产品规格。

**输出：** `RESOLVED_KNOWLEDGE.json`，锁定本轮选中的知识文件路径/SHA/状态、未加载的相邻业务包和覆盖决定。Harness preflight 后续只接受此清单声明的业务规则。

### N2 · 方案设计模块与预期效果预览

方案必须能直接指导制作人员，并把高影响的摆放和美术决定做成可见预览。不得只写方向性文字。N2 的预览是可编辑的设计低保真模型；N4 确认时冻结设计快照，N5 从快照派生工作副本继续细化，复用场景、相机和资产，不覆盖快照，也不从零重做灰模。

`SOLUTION_DESIGN.md` 必须包括：推荐方案及理由、需求到设计元素的映射、符合交付类型的内容结构/布局/对象关系、展示条件与视觉锚点、色彩/材质/光照/背景方向（适用时）、工具与可编辑源、候选目录和版本边界、工作阶段、风险/依赖、预估成本，以及哪些指标自动测、哪些需视觉判断。地图写物件用途/位置/尺度/接地关系；UI 写屏幕布局/状态/安全区；角色或道具写轮廓/比例/结构/展示姿态，不强迫其他品类套地图字段。

附 `DESIGN_PREVIEW_PACK/`，使用与交付类型匹配的低保真预览：

| 交付类型 | 设计预览至少展示 | 预先判断的重点 |
|---|---|---|
| 静态地图、3D 场景 | 目标画幅/机位、灰模布局、主要锚点/遮挡/层级；新风格或光色风险高时必须有粗色光全景与代表材质组合 | 构图、空间关系、对象落地/连接、冷暖层次与远近关系 |
| 可行走地图 | 上述空间预览 + 玩家尺度、路线/阻挡/交互点叠图 | 视觉构图之外，预览路线是否连通、是否被阻挡、交互点是否可达 |
| UI/界面 | 目标分辨率 wireframe、关键状态/页面、交互路径（如有） | 信息层级、可读性、边距/安全区、状态完整性 |
| 角色/道具 | 正侧/关键展示角度的轮廓板、比例/结构标注、有限材质色板 | 轮廓辨识、比例、结构逻辑、与目标风格的细节密度 |

3D 预览用 Blender 固定相机视图、Workbench/低成本实时渲染或可编辑叠图制作；Workbench 只判断布局、轮廓和层级，不能冒充最终材质/光照效果。UI/其他品类使用该产品适合的可编辑 wireframe/mock-up。禁止将 AI 直出图当最终资产；方案预览的目标是提前暴露方向风险，不是伪造最终效果图。

**前置观感验证：**新业务/新画风，或材质、光照、背景衔接、渲染器/色彩管理变化时，N4 前必须补一张粗色光全景和一个代表组合小样。地图小样至少覆盖主体材质、地面和远景的交界；UI 用有代表性的着色界面，角色/道具用带关键材质的展示小样。使用计划中的目标渲染器和色彩管理；允许降低分辨率/采样，但必须足以判断色彩、材质分离与前后景层级。沿用已验证风格且这些条件未变时，可引用原小样 SHA 和适用依据，避免重画。N0 先分配高风险用例 ID/初始判据，N3 在 N4 前补全并检查小样；失败须修设计，不能只凭灰模布局通过就确认视觉方向。低保真无法判断的细节明确留给 N5/N7，不承诺预览等于最终品质。

方案首页突出：`目标效果摘要`、`不可变约束`、`3–5 个主要设计决定`、`待确认问题`、`主要风险`、`验收门槛`。每个待确认项标明需要谁确认，不把问题埋在正文末尾。`OPEN_QUESTIONS` 记录未决事项；一旦决定，结论和依据转入 `DECISION_LOG`，避免两份文档保存不同答案。

**输出：** `SOLUTION_DESIGN.md`、方案预览板、`DECISION_LOG.md` 草稿。

### N3 · 测试用例生成模块

从 `REQUIREMENTS_TRACEABILITY.json` 和方案预览自动/半自动生成 `TEST_PLAN.md` 与 `test_cases.json`。每条用例都包含：`TEST-ID`、覆盖的 `REQ-ID`、阶段、输入/固定条件、操作/比对方式、通过标准、证据路径、检查类型（`mechanical`/`visual`/`manual`）、失败对应的返修规则。数值门槛必须有业务样本/参考依据；尚未校准时用清楚的 rubric 做诊断，标为 `diagnostic_only`，不得伪装成量化 PASS。任何要求都不得没有测试映射。

测试分层，按 `deliverable_type` 生成，不把地图的遮挡/接地测试强加给 UI，也不把 UI 状态测试加给静态图；尽量把问题拦在花费高的正式产出之前：

| 时点 | 主要用例 | 通过证据 |
|---|---|---|
| 需求冻结 | 参考存在与 SHA、范围/交付/禁止项齐全、所有 blocking 问题已解决；non-blocking 假设已记录 | 输入清单、问题单状态、追踪矩阵无孤儿需求 |
| 方案预览（N4 前） | 按产品类型检查布局、核心锚点、结构关系；新风格/光色风险任务必须验证粗色光与代表组合 | 灰模/wireframe/轮廓板，加适用的着色小样、业务 rubric 与证据 SHA；未经验证的细节列为 N5 风险 |
| 首批原型 | 静态地图的体块/遮挡/接地；可行走地图再测路线/阻挡/交互；UI 测层级/状态/安全区；角色/道具测轮廓/比例/结构 | 与设计预览相同展示条件下的原型图、关系清单；失败先改设计和原型 |
| 风格小样（N2 首验、N5 补足） | N2 前置小样确定方向；N5 只补足未覆盖的轮廓、材质、细节与组合风险 | 同展示条件的 style sheet、逐项 rubric 和图像 SHA；不重复制作已经有效覆盖的内容 |
| 完整产物 | 全套视觉评分、硬门槛、图源绑定、输出规格、可重开复现 | 最终图对照、逐项评分证据、源文件与报告 SHA、重开记录 |

**视觉用例**按业务 Profile 选择维度：地图检查构图/地面/空间与物件逻辑；UI 检查信息层级/可读性/状态；角色道具检查轮廓/比例/结构；共同检查色彩、光照、密度与风格统一。必须指出预览/最终图中的具体区域，并绑定证据 SHA。项目一致性与业务参考符合度分别记录。HSV、边缘密度等脚本指标只能在有同类样本和容差依据时使用；否则标记 `diagnostic_only`。机械用例可以自动检查文件、尺寸、展示/渲染参数和哈希；对象关系和重开结果只有在有实际解析器/执行命令时才能声称自动验证，否则应由模型/开发者检查并标明证据，不能把报告字段当作实测。

**输出：** 要求-用例追踪矩阵、每阶段测试清单、测试夹具/参考 SHA、失败修复指向。每个测试标明 `automated`、`model_visual`、`developer_visual` 或 `user_decision` 的责任边界。

### N4 · 开发人员方案确认

方案设计和测试用例完成后，由**实际执行开发的人/模型**做可行性确认，确认内容至少包括：需求是否有遗漏或矛盾、选定的业务知识包是否正确、预览能否表达目标效果、对应品类的工具/源文件/目录是否可用、任务是否能按阶段执行、每条验收要求是否有可操作测试、返修失败时是否知道改哪里。

记录到 `DEV_FEASIBILITY_REVIEW.md`，至少绑定需求、已选知识、方案、设计预览快照和用例的版本/SHA，并记录确认人/模型、时间、逐项检查结论、遗留风险和状态。N4 保存 `baselines/design_rNN/`：包含方案及用例快照、预览图与源文件/依赖清单，由 `BASELINE_MANIFEST.json` 记录 SHA；内容可引用已有冻结文件，避免重复大文件。快照不可原地修改，后续修改设计应另建 rNN 版本并重审受影响项。若方案编写者与实际开发者是同一模型，须在同一任务内做一轮“执行者挑战检查”，无需等待另一模型或用户阶段批准。

**确认失效边界：**N5/N6 派生候选的建模细化、提高采样、在已批准容差内调材质和修正偏离目标的问题，不改变设计快照，不使 N4 自动失效；候选变化仍须更新自己的评分/证据。更换视觉参考、改变已锁布局/机位范围、修改验收条件、业务规则或预算承诺，须返回 N2/N3，形成新设计快照，再做 N4。候选 manifest 记录 `parent_baseline_id`，将实际结果与该不可变快照比较；不得把候选变化后的画面反写成原设计来消除偏差。

状态只能是：

- `confirmed`：范围、方案、预览及前置小样、测试均可执行，可以进入 N5 原型完善及后续批量制作。
- `changes_required`：指出设计/用例缺陷及具体修订项，返回 N2/N3 修改后再确认。
- `blocked_on_user_input`：列出影响画面的关键用户决策；只把这些问题交给用户，不让开发者代猜。
- `blocked_technical`：列出工具/文件/资源障碍和已尝试替代方案。

**只有 `confirmed` 才进入 N5 及后续批量制作。**N2 为验证方案而制作灰模/小样属于设计工作，无须先得到 N4 确认。N4 由实际开发者完成，不要求独立美术终审；已有授权内的技术细化自行处理，只有缺少必要用户决定且无法按已确认边界解决时才请求输入。

### N5 · 低成本原型与早期视觉验收

从 N4 锁定的设计快照派生到未占用候选目录，保持相同展示条件并完善原型；按 N3 用例验证，复用 N2 前置小样并补足当时未覆盖的结构/细节风险。将候选图与不可变预览快照并排对比：偏离已批准目标时先修候选；只有目标设计本身需变更才返回 N2–N4。N2/N5 复用同一资产谱系，但设计快照与可修改候选分别保存，不能互相覆盖。

**扩产门槛：**该交付类型的高风险原型用例通过；代表资产/界面/内容样板在组合中通过主要视觉 rubric；无阻塞问题；开发确认仍有效。小样通过不代表最终产品通过。

### N6 · 受控生产与返修

按当前产品 Harness 执行已确认方案：原型 → 主体内容/资产 → 组合 → 完整产物 → N3 测试集。一次只改一个主要假设；每批记录源、参数/展示条件、命令、退出码、时间、SHA、失败反例和判断。

失败报告必须指向：`TEST-ID/rule_id → 观察到的问题 → 资产/画面区域 → 根因假设 → 源级修改 → 预期变化 → 要重跑的检查`。图片 SHA 改变后，旧视觉评分/通过证据失效；重跑受影响用例，并在最终交付时重跑全量门禁。

**无改善回路：**每次试验在现有返修日志中记录 `hypothesis_id`、`method_id`、前后证据 SHA、固定比较条件、预期改善、实际 `improved/unchanged/worse` 和耗时。改善必须有区域对照/测量依据，不以提高自评分代替证据；修好局部但引入硬门槛失败不算通过。同一问题、同一方法连续两次无改善，下一轮必须换方法或重做根因判断，禁止仅重复同命令高采样渲染。原方法与一种实质不同的替代方法各两次无改善后，标记 `design_recheck_required` 并在同一任务内返回 N2/N3 检查目标、资产选择和实现假设；N4 重新确认必要变更后继续。该标记是返修分支，不是终止或外部阻塞。

N2 为灰模、小样和正式渲染分别记录分辨率/采样档位、预计耗时和升级条件；N6 记录实际制作/渲染/验证耗时。诊断失败优先用低成本档位定位，同一已通过检查仅在输入、依赖或证据失效时重跑。预计超出用户明确的时间/资源上限时，记录预算问题并提出可执行替代方案；没有硬上限时继续在已授权范围内优化。不得为结束任务而降低标准、伪造通过，或把普通返修慢报成 `blocked_external`。

### N7 · 最终验证与交付

用同一版本的 `test_cases.json` 执行最终验收。分别给出机械检查与视觉检查结果；`not_run`、`not_applicable`、`failed` 不能伪装成 `pass`。未通过项应返修并复测；如确有外部技术阻塞，保留完整证据并标记未达标，不伪称通过。

验收逻辑固定为：所有适用的必需用例通过、业务评分达标、硬门槛通过、源/图/报告绑定及复现有效，才可标记交付达标。`not_applicable` 须有已确认范围依据，明确从适用集合排除；必需项 `not_run` 或 `failed` 不可交付为通过。`diagnostic_only` 只帮助定位问题，不计为 PASS，也不代替必需视觉用例。最终图变化后须对当前整图重做全套视觉判断；可复用的机械证据必须证明其自身输入及依赖 SHA 未变。自评通过是制作侧判断，不能声称消除了主观偏差或保证用户一定满意。

交付包需包含本产品可编辑源、最终产物/画面（按交付类型）、绑定 manifest、`TEST_RESULTS.json`、评分与反例说明、预览/关键对照、命令与退出码、耗时和 SHA。视觉评分必须绑定当前最终图/展示图 SHA。

### N8 · 复盘和知识更新

完成后分别记录经验的 `scope`、`lifecycle`、`maturity`，按第 1 节状态契约升级；不再把业务归属、成熟度和废止状态混在一个分类中。每条经验写来源候选、源/图 SHA、适用条件、失败边界、复测次数与责任业务包；回写前查询同类条目，更新原条目或新增有差异的条目，避免重复积累。通用方法满足跨业务验证条件后进入 common；秋日画面答案只进 P1 业务包。失败经验也可记录，但不得进入成功案例库。

### Harness 在接入流程中的职责与现状

Harness 是通用开发层中的**执行与验收控制器**：它消费已锁定的本轮 Brief、业务包和 Harness spec，并管理阶段、候选、检查、失败反馈与结束状态；它不决定所有业务共用一套画风，也不替代制作模型绘图。

| 能力 | 当前 P1 已有的实现 | 对新业务接入方案的状态/边界 |
|---|---|---|
| 项目与会话限定 | 项目级 `UserPromptSubmit`/`Stop` Hook；只在当前仓库、明确 P1 制作请求中 armed，状态按 session ID 隔离，不修改用户全局配置 | 已有，但只覆盖 P1 静态地图；不能当作全产品路由器 |
| 候选与结束控制 | armed 时分配未占用的 P1 `vNN` 候选；Stop 时运行 Gate，未通过会 block 并把修复要求回传同一会话 | 已有；不等于 Hook 会自己启动 Blender 或自动完成修复 |
| 机械质量门 | 核对固定参考 SHA、候选路径、文件存在与 SHA 绑定、评分算术及门槛（总分 ≥85、六维各 ≥3）、四项组合检查、八项硬门槛、修复队列及报告状态 | 已有；它检查报告和证据字段，不会独立证明美术事实为真 |
| 自评反证绑定 | 要求同一制作模型按六维反证，并将反证/自评分绑定当前渲染 SHA；当前不要求独立终审 | 已有的 P1 规则；这是制作侧自检，不是独立视觉认证 |
| 复现/阻塞记录 | Gate 检查重开复现记录与图 SHA；真实外部阻塞须有替代尝试、恢复条件及候选内证据 | 已有记录校验；Gate 本身不启动 Blender 重开/渲染，也不判断阻塞是否合理 |
| 知识按需路由 | 尚无 `business/manifest.json` 和 `RESOLVED_KNOWLEDGE.json` 解析/校验器 | 本方案新增设计；实现后才能保证新需求不会误读 P1 业务规则 |
| 视觉与源场景检查 | 由制作模型看图、判断构图/逻辑并填写对象与零植被证据 | 尚无自动图像质量判断、Blender 场景对象扫描或自动根因修复 |
| 执行与学习 | 制作模型自行调用 Blender；Lessons/知识库由模型或维护者手动回写 | 尚无统一 Blender runner、自动重试、根因分类、知识去重或跨产品效果统计 |

因此，当前 Harness 的实际能力可以概括为：**P1 单项目/单会话作用域 + 候选隔离约定 + 机械证据 Gate + 失败回传闭环**。它能约束报告完整性、哈希绑定和声明的评分门槛，但不能保证画面客观达标，也不是跨业务的自动制作系统。新方案要补的是在通用 Harness 前增加知识路由和运行上下文锁定，而不是把秋日业务规则塞进 Harness 核心。

### 通用化后的运行隔离与启用验收（待实现）

运行上下文固定保存在 `knowledge/active/<request_id>/runs/<run_id>/`，由 `RUN_CONTEXT.json` 绑定规范化绝对 `project_root`、`session_id`、`request_id`、`run_id`、`task_mode`（planning/production）、`business_id`、知识与设计基线、候选绝对路径和检查集。任务 ID 不使用“latest”等会被覆盖的共享名。一个会话的活动指针只指向自身运行；同一候选写入只允许一个运行持有，其他运行使用新候选或只读访问。转交新会话时显式接管并记录原会话、未完阶段及候选，不复制 armed 状态来抢占旧运行。

Hook 分派必须同时核对项目、会话、运行和制作模式，且只在用户明确启动制作时 armed；纯方案讨论、审查文档以及其他项目/会话不进入制作质量阻塞。缺少匹配业务检查器时，在本次任务内报告能力缺口并使用已定义的手工检查，不能回退套用 P1 的 85 分/零植被规则。停止指令和真实外部阻塞按现行控制约定处理，Hook 不能用质量门槛覆盖用户停止请求。上述是目标契约，本次修订不修改现有 Hook 或用户全局配置。

切换前在隔离目录用最小样例验证下表；结果记录在迁移审计中。未通过时修复路由/适配器，保持旧执行入口。先保存旧入口、规则版本和配置 SHA，准备新 manifest/入口并检查依赖；确认没有正在写入的受影响运行后才切换。已有运行继续使用原锁定版本；新运行才使用新路由。回滚只恢复入口/配置指针，不删除候选与证据。

| 场景 | 必须观察到的行为 |
|---|---|
| P1 制作 | 只加载 P1 当前标准；原候选不被覆盖；制作侧自评和机械 Gate 边界保持清楚 |
| 新科幻地图 | 用本业务 Brief/Profile；不因缺少项目美术基线而阻塞，不自动加入 P1 参考或零植被门槛 |
| 本项目纯方案审查 | `task_mode=planning`，不分配制作候选，不触发 Stop 制作质量阻塞 |
| 另一项目/会话，或两个任务同时运行 | 不读写对方状态；候选目录不冲突；并发注册候选须原子占用，不能仅先查存在后创建 |
| 正常细化与设计变更 | 正常候选细化不使 N4 失效；更换参考/验收条件会触发新设计基线及对应复核 |
| 新方法试点与回滚 | 未成熟方法可进入小样但不成为规范；失败切回旧入口后仍能找到原候选和证据 |

| `knowledge/STANDARDS.md`、`knowledge/RECIPES.md` | 拆分后分别归类 | 逐条标记通用核心、交付类型方法或业务专属；避免把 P1 规则继续放在“通用”文件中 |
| `planning/art/STATIC_MAP_WORKFLOW_20261028.md` | `business/p1_autumn_static`；可抽取的通用部分再进 `common/methods/map_art` | P1 当前工作关口留在 P1 包；通用方法只保留一个权威版本 |

| Arknights 地图参数研究 | 独立研究业务包/数据包 | 只为明确提出该数据研究或相关 Harness 任务时加载；不得作为其他产品的视觉参考 |
| `planning/execution/LESSONS.md`、`knowledge/CASEBOOK.md` | 按适用范围拆分 | 通用经验进 `common`；P1 专属经验进 P1 包；未经验证的内容保持 proposed/observed |

迁移每一项前先完成该文件/规则的 `KNOWLEDGE_AUDIT.json` 审计结果：检查是否混写多个层级、是否与其他文档重复或冲突、是否被后续决定覆盖，以及是否仍有活动引用。混合文件要先拆内容、标权威版本、更新旧入口，再移动或归档；禁止直接把整份混合规则复制到多个业务包。审计发现的重复正文只保留在权威源，其他文档保留指针；废止资料保留历史状态，不可继续被活动入口当作执行指令。

P1 业务包中，`STYLE_PROFILE` 回答“参考图看得到什么/要匹配哪些视觉特征”；`DRAWING_PLAYBOOK` 回答“本项目如何用 Blender 原生对象、材质、灯光和镜头把这些目标做出来”。两者通过 `feature_id → recipe_id → TEST-ID` 对应，记录适用候选、源/预览 SHA、参数、步骤、失败反例及分开的 `scope/lifecycle/maturity`。参考可见的原游戏效果与本项目重绘方法必须分开；无法从截图确定的原游戏内部模型/贴图方法只能标为未知事实，不能编造成知识。P1 当前无植被改编应在 Playbook 中作为本项目适配方案，而不是声称还原参考原本植物的绘制方法。

## 5. 标准冲突与选择规则

优先级建议固定为：

1. 用户对本次产品的最新明确要求。
2. 本次 `REQUIREMENTS_BRIEF.md` 中明确的目标、范围与覆盖决定。
3. 本次选中的、已启用版本的业务包 `BUSINESS_PROFILE` / `STYLE_PROFILE` / `HARNESS_SPEC`。
4. 经用户确认的项目级 `ART_STYLE_BASE.md`。
5. 同类产品中验证通过的 `reusable` 案例。
6. `observed`/`proposed` 经验和外部工具建议。

前四项决定本次验收要求；文件规范须为 `lifecycle=active`，用户当前明确要求直接作为启用依据记录。后两项仅支持方法选择或试验，不能覆盖验收要求；draft 方法可以按 experiment 方式进入小样。`superseded`、`deprecated`、`historical` 文件不能参与当前规则裁决，修改时间较新也不能自动使其成为权威来源。通用开发层管理 Harness、证据、版本和结束条件；业务包管理产品内容与视觉规则，不能自行改写通用状态契约。Brief 在用户明确依据下覆盖美术基线时，须记录 `inherit/override/not_applicable`。活动业务规则冲突时写入 `conflicts_and_decisions`；不能按加载顺序择一。仅当本次相关冲突无法按已有决定解决时才标 blocking，暂停受影响项，继续不受影响的工作。

旧文件、单次候选结果和外部参考不得越级覆盖新 brief。发现冲突时先在 brief 的 `conflicts_and_decisions` 记录，不可默默拼接两套风格。

## 7. 建议实施顺序与依赖

先把最小流程做成可人工执行的标准，再自动化路由和检查；不要把所有 P0 文档/脚本一次性做完，才允许第一个业务试点。

| 顺序 | 行动 | 完成标志/依赖 |
|---|---|---|
| P0-1 知识清理审计 | 建文件索引，先审本次活动入口/业务及依赖；日常只审新增变更，结果写入 `KNOWLEDGE_AUDIT.json` | 每项有唯一来源、分离的状态、SHA、动作和引用检查；只阻塞本次相关冲突，无关历史清理分批推进 |
| P0-2 项目入口与权威源修订 | 在迁移草案中拆分 AGENTS/START_HERE 的通用与 P1 规则，修订冲突的执行指南和索引；待 P0-5 检查后启用新入口 | 草案入口只指向已审计权威源；每项规则有唯一正文；检查完成前保持当前执行入口 |
| P0-3 设计前置 | 建立统一命名的需求/设计/用例/确认模板及设计快照 manifest；小任务可用章节合并文档 | 每条需求有用例；新风格有前置着色小样；N4 状态取值与正文一致；正常细化不使快照确认失效 |
| P0-4 整理现有 P1 知识 | 按审计决定把 P1 视觉事实、绘制适配方法、研究假设、案例状态分开，建立 `STYLE_PROFILE` 和 `DRAWING_PLAYBOOK` 的索引/草案 | 明确引用经审计的 P1 标准、工作流和 Lessons；不复制出多套冲突标准；明确当前没有已验收成功案例 |
| P0-5 手动路由与切换契约 | 人工填写 RUN_CONTEXT/RESOLVED_KNOWLEDGE，锁项目/会话/任务/运行和业务；用第 3 节样例核对人工路由、文档引用、目录和快照，准备回滚指针 | P1、新业务、纯讨论分别进入正确流程；检查后启用文档入口，旧运行保持原版本；Hook 隔离/并发自动化样例仍标待 P1-2 实测，不能声称已验证 |
| P0-6 美术基线（可选） | 整理候选 `ART_STYLE_BASE` 并请求用户确认 | 未确认时为 `lifecycle=draft`，不作为硬门槛；不阻塞已有明确视觉参考的新业务 |
| P1-1 新业务试点 | 选一个真实新需求，先按模板手动运行 N0–N8；N2/N5 必须做低保真视觉预览和前置验收 | 记录误路由、漏需求、开发确认发现的问题、预览预测误差、返工和耗时；无需等待路由代码 |
| P1-2 Harness preflight | 根据试点结果实现路由/检查适配器，核对运行身份、制作模式、业务版本、需求-用例覆盖及设计确认；重跑第 3 节全部隔离与切换样例 | 只阻塞对应制作运行；缺必需件指明字段；纯讨论/其他项目不受影响；测试通过才切换 Hook，保留回滚 |
| P1-3 视觉门禁接线 | 将对应品类的低保真预览/原型验收状态接入 Harness | 与 N2 预览同条件对照；偏差回到方案或原型阶段；不得把人工视觉判断伪称为自动图像评分 |
| P2 规则自动化 | 仅将重复、客观、证据可靠的测试写成可执行 validator | 报告明确区分自动、模型视觉、开发者判断和用户决策；失败能指到 test/rule ID |
| P3 知识成熟 | 按 scope/lifecycle/maturity 分别维护；业务内小样可支持本次扩产，通用经验须至少两个业务包复测 | 跨业务验证有效且带边界/反例后才升级为 common 的 reusable；首次业务没有成熟案例也可受控试验 |

目前尚未定义被用户批准的项目级完整美术 Style Bible，也未实现按需知识路由，因此本文件只提出分层、路由机制和接入框架；不能据此声称已经有一套可直接复制的统一产品画风。项目美术基线尚未批准不应阻止有明确业务参考的新需求；只有用户希望跨产品共用某项视觉原则时，才将该原则确认后升级为通用规则。

## 8. 可借鉴的公开实践

以下资料用于设计方法，不代表照搬航天或 Unreal 项目的全套流程：

| 来源 | 可借鉴做法 | 本方案中的落地 |
|---|---|---|
| [NASA Systems Engineering Handbook：Fundamentals](https://www.nasa.gov/reference/2-0-fundamentals-of-systems-engineering/) 与 [Product Validation 章节](https://science.nasa.gov/wp-content/uploads/2023/04/nasa_systems_engineering_handbook_0.pdf) | 明确区分“是否按要求做对”（verification）与“是否做对了用户要的产品”（validation）；可以在早期用模型、mock-up、模拟等阶段产物验证方向，不必等完整产品 | N0 建立需求/验收追踪；N2–N5 对方案预览、灰模和风格小样逐级验证，问题前置发现 |
| [Blender Camera View 手册](https://docs.blender.org/manual/en/5.3/editors/3dview/navigate/camera_view.html) 与 [Workbench 手册](https://docs.blender.org/manual/sr/5.2/render/workbench/index.html) | Blender 相机视图可预览实际画幅构图；Workbench 适合快速建模/动画预览，但不是最终材质渲染 | 固定相机和画幅做设计灰模；Workbench 检查轮廓/遮挡/布局，粗色光与最终观感另用目标渲染器验证 |
| [Epic Unreal Data Validation](https://dev.epicgames.com/documentation/unreal-engine/data-validation-in-unreal-engine?lang=en-US) | 把命名、性能预算、依赖等客观规则写成自定义 validator，可对单资产、文件夹、项目及命令行批量运行 | 借鉴“规则即检查器、失败即阻断”的方式，为 Blender/项目工具逐步建立可重复的机械检查；不引入 Unreal 作为本项目工具 |

**结论：**最有价值的改动是“先把验收方案写出来，再开始制作”，并让灰模/关键资产样板成为设计评审材料。NASA 的早期验证、Blender 的相机预览和 Unreal 的可脚本化校验各自解决不同问题；组合后可以提前看构图和方向、提前检查客观约束，但主观美术质量仍需要固定参考、具体 rubric、绑定图像证据和返修闭环。
