## 0. 一句话

四卡到不了 90，不是"再改两处参数"。是三层叠加：**画面上限**（场景内容与资产预算）→ **度量错配**（自评比独立高 8–16 分）→ **证据通胀**（一部分覆盖率是画出来的，不是玩出来的）。

## 8. 本轮实验（D2 绿篱减叶）

**改法**：`_hedge_leaf_skin` 增加 `keep` / `keep_back`，`courtyard_lib.add_leaf_cluster` 增加 `keep`。系数由环境变量 `N5_HEDGE_KEEP / N5_HEDGE_BACK_KEEP / N5_HEDGE_FAR_KEEP / N5_HEDGE_FAR_BACK_KEEP` 控制，默认全 1.0，不设变量时构建结果与改动前一致。

**关键做法：减叶但照旧抽签。** 每片被跳过的叶子，它的随机数仍然全部抽完（位置、尺寸、自转、材质、倾角），只是不建几何。因此 RNG 流不变，绿篱之后构建的每个网格逐顶点一致。实测 176 个网格中 **174 个顶点位置哈希完全相同**，只有 `bg_hedge_cards` 与 `bg_hedge_far_cards` 变化。像素差因此只可能来自被移除的叶片，不会混入"重新随机"的噪声——这一点比 D1 的 A/B 干净得多。

**采用值**：`KEEP=0.55 / BACK=0.0 / FAR=0.40 / FAR_BACK=0.0`。绿篱是环形围合，背面（朝墙外）的叶片卡被闭合的实体体积完全遮挡，整面归零；正面只在轮廓线以下减，`t>=0.9` 的顶层与顶盖不参与减密。

|---|---:|---:|---:|
| 近排叶片卡 | 352,784 | 192,464 | −45.4% |
| 远排叶片卡 | 114,840 | 56,760 | −50.6% |

**同机位图像对比**（Cycles，正式相机）：全帧平均差 **0.53/255**，>8 占 1.41%，>24 占 0.40%，顶部 120 px 变化 2.00%，铺地区域 0.02。

## 9. 更正：Cocos 启动失败的真实原因（2026-10-26 11:05）

D1/D2 两节都写了"本机 Cocos Creator 起不来"。这个说法只对了一半，必须更正：**编辑器程序本身没坏，坏的是它拉起的那个沙箱化 GPU 子进程。**

**事实**：今天 Cocos 成功构建过 20 多次，最近一次 09:09（`cocos_build_20261026_090949.json`，exit 36 + SIGTERM + success marker）。全部使用同一条命令：

```
CocosCreator.exe --project .../demo_n5 --build configPath=.../build-config-web-desktop.json
```

**失败形态**（10:24 / 10:26 / 10:54 / 10:56 共四次，含一次在工具沙箱之外执行）：

```
ERROR:gpu_process_host.cc(1002) GPU process exited unexpectedly: exit_code=-1073741819   (x9)
FATAL:gpu_data_manager_impl_private.cc(449) GPU process isn't usable. Goodbye.
→ exit 2147483651
```

`-1073741819` = `0xC0000005` 访问违例。崩溃发生在启动后 2 秒内、"加载内置引擎成功"之后、项目加载之前，所以**不是工程文件问题、不是命令行参数问题**。

**已排除的假设**：

| 假设 | 做法 | 结果 |
|---|---|---|
| 相对路径不对 | 改用记录里的绝对路径 | 仍崩 9 次 |
| `NODE_OPTIONS` 注入（shell 里指向 workbuddy 的 node shim） | `env -u NODE_OPTIONS` | 仍崩 9 次 |
| 工具执行沙箱挡了 GPU | 跳出沙箱执行 | 仍崩 9 次 |
| 显存/显卡异常 | `nvidia-smi`：RTX 4060，1.2/8.1 GB，驱动 610.88，状态正常 | 排除 |

**有效解法**：三种开关都能让它起来，说明坏的是"沙箱里的独立 GPU 子进程"这一条路径，而不是某个具体 GL 后端：

| 开关 | 结果 |
|---|---|
| `--in-process-gpu`（GPU 线程并入主进程） | 构建成功，GPU 崩溃 0 次 |
| `--disable-gpu-sandbox --no-sandbox` | 构建成功，GPU 崩溃 0 次 |
| `--use-angle=swiftshader --use-gl=angle --disable-gpu-sandbox` | 构建成功，GPU 崩溃 0 次 |

**构建产物无关**：用开关重建后的 `application.js` / `src/settings.json` / `src/import-map.json` 与 09:09 那次**逐字节相同**（`3876486e…` / `ce1789fe…` / `ae84a42b…`）。这些开关只影响编辑器宿主，不进入产包。

**已落到工具里**：`tools/cocos/build_web_desktop.py` 现在默认追加 `--disable-gpu-sandbox`，并额外摘掉 `NODE_OPTIONS`；可用 `COCOS_EXTRA_ARGS` 覆盖。命令与开关会写进 `build_report.command`，便于以后核对。

**对 D1/D2 的影响**：D1、D2 的"引擎证据缺失"现在**是可补救的**，不再是硬阻塞——把新 GLB 拷进 `demo_n5/assets` 重新构建、再跑一次 canvas 截图即可。在那之前，两张图仍然只有 Cycles 证据。

## 10. 引擎实测：两处做法被推翻后重做（2026-10-26 11:33）

Cocos 加 `--disable-gpu-sandbox` 能起来之后，第一次真正在引擎里看这两刀，抓出两个问题。

**问题一：D1 的草按"少种几丛"减，环坛被重排。** 丛数一变随机流就变，环坛的草位置整体重来，中间空出一片裸土。当时 Cycles 只测到 3.30/255，我写了"环坛溢出感保住"；引擎实测 **14.81/255、39.4% 像素变化**，低估四到五倍。

**问题二：构建漏了 `N5_PAVING_VARIANTS=1`。** 铺地四种砖型由这个变量控制，不带它 16 块全塌成 0 号变体，`paving_slabs` 从 7,680 涨到 9,216（+20%）。与随机流无关，是没复现原始构建参数。变体序列应为 `[2,3,0,3,0,1,0,1,2,1,2,3,3,1,2,2]`。

**做法改成一件事：只减几何，不动随机数。**

- 草改为**单根草叶**级减密（`N5_GRASS_BLADE_KEEP`）。`_add_blade` 不消耗随机数，所以每丛位置不变、草之后构建的网格全部逐字节一致。环坛单独给 `N5_GRASS_RING_BLADE_KEEP=0.55`，因为它是每张图的正中心。
- 绿篱沿用照旧抽签法：背面归零、正面只减轮廓线以下、顶层与顶盖豁免。
- 铺地补回 `N5_PAVING_VARIANTS=1`。

| 总三角面 | 1,445,953 | **912,613** | −36.9% |

| 环坛 | — | 4.39/255 | 从 14.81 修回 |

构图未动：对 ±6px 位移搜索，最佳偏移 (0,0)。

## 11. 综合结论：90 分是算不出来的（2026-10-26 12:00）

前面十节是分项取证，这一节是总账。**结论：瓶颈不是模型能力，是"规格与目标互斥"这件事被一套测不准的尺子包着，掩盖了四轮。**

### 11.1 先把分数拆成算术

评分公式是 `Σ(权重 × 档位) / 4`，六维权重合计 100。所以**一档 = 10~25 分**，不是"一分两分"。

自评门槛 90 只是提交过滤；独立验收线是 rubric 85。两者之间有 8~16 的系统偏差（n2 平均 −8.4，n4 平均 −10）。所以：

> **想过独立 85，自评得先到 96~97。**

按这个目标重算三张卡：

| 卡 | 现状 | 到自评 96+ 需要动的维度 | 动完 | 可行性 |
|---|---:|---|---:|---|
| UI | 87.5 | typography 3→4、doodle_icon_family 3→4 | 97.5 | **可行**，纯排版与图标，不需要新资产 |
| MIX | 80.0 | visual_language 3→4、color_light_coherence 3→4、再一维 | 96.25 | **可行**，但要一次美术方向决定 |
| ENV | 77.5 | 四个核心维里至少三个到 4，且**必须含 geometry_craft** | 95.0 | **不可行**，见 11.2 |

### 11.2 ENV 为什么不可行：两个核心维被锁死

ENV 四个核心维（composition / geometry / material / lighting，各 20 分）现在全部是 3。数学上最多只能留一个在 3，其余三个必须整档跳到 4。而这四个里有三个不是"努力"能动的：

| 维度 | 锁在哪 | 证据 |
|---|---|---|
| composition_scale | Q01 规定角色可见高度 86–130 px（720p 下约 18% 屏高）→ 相机只能拉远 → 铺地占半屏 | 产线自算：`n5-a0-02` "Flatter/closer framings push the feet to y=748-940, i.e. off the 720 frame" |
| geometry_craft | 3D 部分只有 4 种可读物体（树/环坛/长椅/路灯），且是平面着色的程序化基本体 | 与 P1 t015 对比：P1 画面 10–12 种可读物、三层前后遮挡 |
| material_separation | 铺地 7,680 面承接半屏面积，磨损靠噪点而非裂/苔/磨边 | 已改三轮，分数始终 3 |

**把这句话算成数**：假设 composition 与 geometry 都停在 3（现状），只把 material、lighting、readability、vegetation 全部推到 4：

`20×3 + 20×3 + 20×4 + 20×4 + 10×4 + 10×4 = 360 → 90.0`

**这是 ENV 在这个规格下的数学上限。** 保守一点（readability 不动）是 87.5。而想过独立 85，自评需要 96 —— **差的 6 分只能从 composition 或 geometry 这两个被锁的维度里出，没有第三种可能。**

### 11.3 归因：四层，按"咬得多死"排序

| 层 | 内容 | 是不是瓶颈 |
|---|---|---|
| 一 · 规格 | Q01 锁构图、4 种物体锁几何、1.45M 面/112 MB GLB 锁上线 | **是第一因**，数学上封顶 |
| 二 · 度量 | Cycles 比引擎低估 4–5 倍；构建输入不可复现；自评系统性 +8~16；41 状态里 8 个不可达、3 张规范图；47 份复核同一句话 | **放大器**，让第一因迟了四轮才被发现 |
| 三 · 产能 | 6.65 h 里只有 29.8 min（7.5%）被计量；参数微调替代工艺；并行代理失效；2569 行单文件、0 测试、无 CI | **减速器**，每轮只能挪 2–3 处 |
| 四 · 模型 | 分不清 3 和 4、雕不出工艺、不知道"够了" | **只在最后 10 分封顶**，不是前 80 分的原因 |

### 11.4 反向证据：同一个模型，今天做了什么

今天我自己在这个仓库里做了三件事，恰好把这套流程的三个病各犯了一遍，然后又修掉了：

1. **按丛数减草** → 随机流跟着变 → 环坛裸土。Cycles 测 3.30/255，我写了"溢出感保住了"；引擎实测 **14.81/255、39.4% 像素变化**。这就是项目一直在犯的错：**拿代理指标当验收**。
2. **提交里写"其余网格未变"** → 实际 `paving_slabs` 7,680→9,216（+20%），因为漏了 `N5_PAVING_VARIANTS=1`。项目历史上同一个坑：铺地哈希恒等于 0，16 块里 15 块没变，当时没人发现。
3. 改成叶片级减密后：**1,445,953 → 912,613（−36.9%），171/176 网格顶点哈希逐字节相同，引擎整帧差 2.64/255。耗时约 90 分钟。**

第 3 条是关键反证：**同样的模型、同样的机器，给定单一目标 + 真实闭环（构建→引擎帧→像素差→逐网格哈希），90 分钟做出了四轮没做出来的可验证结果。** 所以卡住的不是模型的手，是流程里没有那个闭环。

而模型真正做不到的是另一件事：**我到现在也说不出这张图是 3 分还是 4 分。** 这个天花板是真的，但它坐在判断端，不在执行端。
