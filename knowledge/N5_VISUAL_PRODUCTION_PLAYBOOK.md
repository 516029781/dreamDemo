# n5 美术返修制作配方：从结构到最终画面

更新：2026-10-26。适用 `candidate_n5`；这是**制作指导和待验证假设**，不是 n5 已完成或 90 分保证。以有效合同、`art_review/rubric.json`、`planning/execution/producer_review_policy.json` 和活动返修指针为准。n2/n4 源、构建、截图只读；所有修改先复制并参数化到 n5。当前证据：P1 `reference/_raw_screenshots/P1/t015s.jpg`、`t044s.jpg`，n4 `delivery/next_cycle/n4/T3/game_finalN4_formal_no_ui.png`、`game_finalN4_dialogue.png` 及 n4 预审报告。

## 0. 先改变制作方法

n4 的主要失分是**构图、几何层次、UI 遮挡和角色接地**。这些属于结构问题。先用同机位灰阶/剪影和真实 Cocos 画布判断结构，再处理表面纹理和装饰。禁止以增加随机叶卡、地面噪声、涂鸦数量或整体滤镜来代替结构返修。每批只检验一个共享原因；先保存原图、变更参数和预测，再改源并拍同镜头。三次无改善就改变构造机制，不继续改随机种子。

**第一轮最小样板**：一张 1280×720 无 UI 全景、一张树/花坛近景、一张对白同屏。只在这三张上看到明确改进后，才扩到全部状态和 47 组复核。样板不替代最终完整 Q/绑定。P1 与本项目镜头并非同一场景，P1 用于风格、密度与视觉关系对照；判断本项目修改是否有效，只比较 n4/n5 的同位置、同镜头、同状态原图。

**先把“达到 90”拆成可观察结果**：独立 rubric 的维度分是 0–4，制作侧 90 筛选不能由“总体看着更好”推算。每批在 `decisions.jsonl` 写出它可能改变的具体维度、原分/预期分、两张支持该分的实际画面和一个反例。局部样板只决定是否值得继续制作；只有所有批次完成、正式画布与行为证据同源后才重新逐维评分。不要把下文的像素余量、叶片数量或组合数量写成新的评分标准。

**诊断先于选任务**：先把 n4 无 UI/有 UI/对白三张原图并排，按 `rubric.json` 标出每张图最大的三个可见缺陷，以及它们影响的维度。优先级用“预计能关闭的严重缺陷 × 受影响画面数 ÷ 试验成本”排序，并在日志记明理由；这只是排序方法，不是自动美术评分。默认先做相机/构图的低成本灰盒判定，再做树与远景，随后材质、对白和 MIX。若对白遮挡使角色只露头等问题能用一次 UI 样板快速证实改法，可与环境批次独立试验，但正式选择须等全局相机定稿。不要仅因 n4 ENV 自评分高于 UI，就假定树一定是最高收益项。

## 1. ENV-1：树冠与远景，先修“叶片有根”和深度

**观察和源码定位**：n4 全景的主树像细碎叶卡噪声，远景顶部是一整条暗色块。`tools/blender_n4/build_env_courtyard.py` 的 `_grow_branch()` **已经记录 `tips` 和 `anchors`**；问题是 `create_tree()` 另有 `for i in range(112)`，把内层 sprig 随机放在冠体积中，绕开了已有枝锚点；`_add_leaf_sprig()` 每个 sprig 又生成两层大量叶片。`tools/blender_n4/build_map001.py` 同时生成连续北侧绿篱、后排绿篱与远处 `_hedge_volume` 带。这是待验证的主因假设，不代表删掉 112 处后必然达到 P1。

**具体做法**：

1. 先复制 n4 脚本到 n5，保留 `_grow_branch()` 现有 `tips/anchors` 输出。做**同一树种子下的三图消融**：A 原版；B 仅关闭 112 个体积 sprig；C 关闭它们并从已有 `anchors` 沿枝方向补少量叶簇。三图固定镜头、灯光和导出参数，记录叶簇数、tri 与剪影。若 B 消除了浮叶但变稀，再用 C 补；若 B 仍乱，检查现有末梢叶簇、树冠质量块和相机，不继续在体积里撒点。只在现有锚点不足时扩展 `_grow_branch()` 输出真实中段线段与父子关系，再沿线取样；不要先重写整套分枝算法。先关叶查看枝干粗细递减和可读空隙。
2. 再用三层受控叶簇建立轮廓：深色内层只填主枝后方，中层形成数个不等大小的团组，外层只在真实末梢留不规则叶缘。先用低叶量预览，必要时分批增加；每次记录总叶片/三角面，不把叶量增加当成功。内层 `crown_mass` 不应从外轮廓露出球状边界。
3. 在单体预览里生成一张**纯黑剪影**和一张枝线可见图，标出任何离枝叶簇；再做游戏相机距离预览。只有剪影、枝干和空隙都成立才启动 `env_tree→map001`。若剪影仍是“球+散点”，先改枝线/宏观叶团位置，不调材质。
4. **树试验选定后再单独改远景**。先分别关闭远处 `band_bm`、第二排绿篱、北侧近绿篱，固定全景找出造成暗带的层；只改确认的层。将它切成有开口、高低和亮度递进的可编辑段，保留围合空间感与必要的视觉边界；不能在未确认遮挡关系时同时删除三层。已有碰撞/通路不动，远景对象仍无碰撞。若暗带消失但背景变空，用低对比建筑或树冠轮廓补深度，再与 n4 原图对照。

**收件与退回**：交 `ENV006` 的枝线/剪影/近景及 MAP001 同机位全景、对象/叶片/tri 统计、变更前后文件 SHA。若第 0 批改了镜头，树消融 A/B/C 都用**新镜头**；n4 原图只供历史观感参照，不声称与新镜头同机位。审核者在游戏视距能看清主干→分枝→叶团关系，找不到明显无枝承托叶团，后景至少读出前中远关系。若树单体好而全景仍乱，检查相机、前后层遮挡与色值；不要再次加叶。

**性能边界**：Blender Geometry Nodes 的分布/实例可帮助维护同一叶簇母版，但实例经导出后能否保留渲染收益取决于 GLB 与 Cocos 实际路径；必须量最终 Q06，不将 Blender 视口流畅当作微信性能。[Blender 分布节点](https://docs.blender.org/manual/en/3.0/modeling/geometry_nodes/point/distribute_points_on_faces.html)、[实例节点](https://docs.blender.org/manual/id/dev/modeling/geometry_nodes/instances/instance_on_points.html)。
**成本纠偏**：n4 全景约 553 draws、1,552,913 tris，已经高于当前 Q06 的 400/400,000 预警线。n5 对每个 A/B/C 变体同时记画质与成本；“不比 n4 更差”不足以说明性能可用。若 C 的叶簇质量提高但面数继续上升，先做同一剪影下的叶片数、面片层数、远景可见范围消融；最终由实际 Cocos 和微信设备结果决定取舍，不能以 Blender 实例数直接推断运行成本。

## 2. ENV-2：铺地与构图，做“有组织的空间”，不撒随机杂物

**观察和源码定位**：n4 全景中大面积重复浅色砖占中心，长椅与花坛各自孤立；P1 t015s 的铺地仍可走，但有树影、座椅、栏杆、台阶、标识和前景遮挡形成连续的视觉路径。`tools/blender_n4/build_map001.py` 的 `PAVING_CENTERS` 拼多个 4×4 模块；`env001_stone_paving.py` 用固定 `EVEN_X/ODD_X` 网格，重复模数在远景很明显。

**具体做法**：

1. 先把当前游戏相机帧划成前景边缘、角色通路、主树/交互中景、远景四区；在一张俯视布局图上画出玩家至园丁/留言板的实际可走线。保留当前碰撞和交互坐标，路面净宽以有效布局合同为准。
   **源修改前**做两张低成本灰盒相机候选：A 保持 n4 正式机位，B 小幅改变俯角/距离。两张都用同一世界与分辨率，不同时改光、贴图和摆件；逐张记录角色屏幕 bbox、主通路、NPC/交互点、树前后遮挡及画面边缘裁切。若 B 的层次更清楚且 Q01/交互/遮挡无回退，才选 B；否则保留 A。相机变更会使正式截图、Q01/Q03、UI 遮挡与评分全部重新采集。此处灰盒只用于决策，不冒充最终游戏构建或 Q 证据。
2. **只在通路边缘**增加两组有功能的空间组合，例如“长椅+灯+少量落叶”与“花坛+导视+高低植物”；让现有 `PROP001/PROP004/PROP005/ENV007/ENV008` 形成组合，不新造一批无用小道具。每组至少有低、中、高三个读形层，前景可用已有栏杆/植物做局部遮挡；中心行走面保留留白。
3. 地砖改为可复用的 2–3 个原生变体：接缝错位、少数边角磨损、受控的明暗分组；对单张 4×4 模块和全图分别看。只换贴图色相、保留完全相同的几何模数，会继续显重复。变体的 UV/材质仍共享或受控，记录新增三角面与材质槽数量。
4. 固定相机先看**无材质灰阶**：角色、树、互动点是否在视觉动线上，前中后景是否分开；再恢复材质看石/木/金属分辨率。若全景仍由空砖主导，调整组合的位置或镜头构图，不用增加纹理噪点。

**收件与退回**：交布局俯视图、可走路径/碰撞检查、n5 改前/改后同机位全景与两处近景；若沿用 n4 镜头再加 n4 历史对照。要求主路径清楚，互动对象能找到，中景有可辨功能组，远景不再是一条暗墙。若组合挡住移动/触控交互，先退回布局调整，不接受“画面更满”作为通过。

## 3. ENV-3：材质和光照，按游戏引擎最终表现校准

**观察和源码定位**：n4 已有 1024 级程序化石/木纹，`demo_n4/assets/scripts/CourtyardBootstrap.ts` 的 `MAT_OVERRIDES` 又给材质加色值、roughness、metallic 与运行时 normal/pbr map。画面仍显平，说明继续提高纹理分辨率未必有效。方向光、填充光、树影和地砖亮度一起决定最终对比。

**具体做法**：

1. 在 n5 Cocos 中做一组**固定光照、固定相机**的石块/木长椅/金属灯杆同屏试件。先看纯 base color，再逐个开启 normal、roughness/pbr，记录每层对可见形状的影响；异常时检查贴图的线性/sRGB 用法及 UV 尺度，不把颜色纹理当法线替代。
2. 石材先使接缝和倒角在游戏视距可辨，再加低频色差；木材按板长方向对纹，金属用 roughness/高光与木石区分。明确为每种材料设一个母版，不为同一物体生成多份近似纹理。Blender 的节点外观不能直接视为 Cocos 最终结果。[Blender Principled 材质参数](https://docs.blender.org/manual/en/4.0/render/shader_nodes/shader/principled.html)。
3. 灯光只做一项变更再截图：主光方向→接触影→填充强度/色温→远景对比。记录角色脚底、长椅下缘、花坛接触、树影四个锚点。若亮暗关系不清，先改主光与局部遮挡，不直接加后期对比滤镜。`shadowMapSize=4096` 已是 n4 的成本项；降分辨率/阴影距离需和真实画面、Q06 一起比较。[Cocos 定向光与阴影参数](https://docs.cocos.com/creator/manual/en/concepts/scene/light/lightType/dir-light.html)。

**收件与退回**：交同一 Cocos 构建的无贴图/最终材质对照、三材质近景和全景、灯光参数、draws/tris。若近景可辨而全景无区别，检查对象尺寸、相机/照明或色值，不再盲加纹理细节。

## 4. UI：先解决人物遮挡，再统一纸面笔触

**观察和源码定位**：n4 对白 `DIALOGUE_W=1060`、`DIALOGUE_H=176`，在 1280×720 中的宽高比例已经接近 P1 t044s；主要错误是角色脚下落在面板区域，n4 对白图里只露头。`demo_n4/assets/scripts/CourtyardBootstrap.ts` 的 `buildDialogue()` 把纸面放在中心坐标 y≈−262，顶缘约 y=−174；同文件已有 `projectToCanvas()` 可返回玩家头/脚屏幕坐标。当前继续压面板高度会伤文字可读性，增加涂鸦也不能解决遮挡。

**具体做法**：

1. 先做**不改世界坐标的 UI/取景 A/B 样板**：A 暂时只调面板位置/宽度及半透明边缘；B 保持面板可读尺寸，改对白相机取景。两组都在真实画布上记录玩家 head/feet、NPC、面板与触控区边界；选择角色全身可见、文字/点击区完整且互动目标不丢失的一组。若选 B，必须在 n5 的每帧相机更新里加入明确的 dialogue 模式或优先级：n4 `update()` 在 `cameraMode==='game'` 时每帧重设相机，单在 `openDialogue()` 里 setPosition 会立刻被覆盖。对白打开/关闭、暂停、竖屏返回和调试 inspect 切换均要验证相机恢复与玩家/任务状态。脚点高于面板顶缘约 12–20 px 仅是初始试验余量，以实际角色透明区域和面板安全区检验，不是合同阈值；`projectToCanvas()` 预测值还要与真实截图的可见边界核对。
2. 对白状态的左上任务卡若争夺焦点，使用同一状态机隐藏或压低其视觉权重；关闭对白恢复，不改变任务数据。先采 n5 真实 canvas：普通、对白第一页/第二页、退出对白、移动后再对白。若人物仍被遮挡，优先调相机预设或对白布局，**不**剪裁角色图。
3. 保留现有可编辑 `paper_panel.svg` 与 9-slice 导出路线；让对白、任务卡、交互按钮共享同一纸边、描线、字体层级和装饰色。先制作一张包含三组件的样板页，删掉与信息无关、重复的纸屑/涂鸦，只在头像和按钮附近留少数呼应的笔触。纸面透明度用真实铺地和树影背景检验，小字可读性优先。Cocos 九宫格用于保持边角形状，不保证内容排版正确，仍需逐状态真画布验收。[Cocos 九宫格说明](https://docs.cocos.com/creator/3.8/manual/en/ui-system/components/engine/sliced-sprite.html)。
4. 检查 1280×720 与 720×1280 的中文文字、头像、下一页触控区、关闭键；竖屏按当前合同提示/锁输入，不把静态截图当行为通过。静态涂鸦若由大量独立 Graphics 节点绘制，可优先统一 SVG/图集以降低 UI 批次，但先测 draw calls，不能为合批牺牲可编辑源或画面。[Cocos UI 合批条件](https://docs.cocos.com/creator/3.8/manual/en/ui-system/components/engine/ui-batch.html)。

**收件与退回**：交人物 head/feet 对面板 bounds 的记录、4 状态真实画布、三组件 SVG/九宫格母版、字体/触控检查。第一道门只看人物全身和对白可读；过了再审纸面风格。若角色仍被遮住，不因涂鸦丰富或面板高度达标而给 UI/MIX 高分。

## 5. MIX：固定同一时刻做角色接地和风格融合

**观察和源码定位**：n4 世界角色是 `RenderTexture→world transparent quad`，接地影是运行时径向纹理放在 1.72×1.12 世界平面；NPC 也有类似影。n4 图里影子像贴片，角色精细而地面/远景粗。角色源已锁定，应改环境、相机和影子接触，不重画角色。

**具体做法**：

1. 在同一角色世界位置和相机时刻拍无 UI、有 UI、对白三图。用 debug 标出角色脚点投影、影子中心、地面接触点；先保证三者重合。制作两档较小、更淡的接触影试件与 n4 原影并排，选能接地但不形成深色椭圆的一档；尺寸/透明度以实图确定，保留可调源参数。
2. 树前/树后移动用真实输入验证正确遮挡。人物的暖色调整只做轻微一致性修正；若角色依旧像贴在背景上，先回 ENV 的几何、材质和光照，不对人物加全屏滤镜。
3. 把 MIX 的观察拆成四项：脚底接触、遮挡顺序、角色/场景同向受光、UI 对人物焦点的占用。逐项用图和状态说明，不用“整体和谐”一句话代替证据。

**收件与退回**：三同机位图、前后遮挡状态、影子参数对照和 MIX 逐维诊断。若 ENV/UI 核心缺陷仍开着，MIX 不单独堆特效“冲分”。

## 6. 一轮制作的顺序与停止错误尝试的方法

| 批次 | 原生修改位置（从 n4 派生 n5） | 先看什么 | 何时升到 Cocos | 失败后换什么方法 |
|---|---|---|---|---|
| 0：基线与镜头 | n4 三正式图；同场景 A/B 灰盒相机 | 角色 bbox、通路、交互点、层次 | 选定正式镜头或保留原镜头 | 不为镜头牺牲玩法/Q01/Q03 |
| A1：树 | `build_env_courtyard.py` 现有 `tips/anchors`、体积 sprig | A/B/C 消融、枝线、剪影 | 已确定叶量/拓扑的有效变体 | 停止加叶；回查末梢/冠体质量块 |
| A2：远景 | `build_map001.py` 各层绿篱与远带 | 逐层开关的固定全景 | 找到暗带责任层并改出纵深 | 恢复围合边界，换轮廓而非只调色 |
| B：路面构图 | 相机候选、`PAVING_CENTERS`、铺砖母版、现有道具布局 | 灰阶全景、可走线、Q01/Q03 | 组合不挡路且视觉路径清楚 | 调道具组合/相机，不撒磨损噪点 |
| C：材质灯光 | 纹理母版、`MAT_OVERRIDES`、主光/影 | 三材质同屏试件 | 引擎视距可辨差异 | 查 UV/贴图通道/光，不只升分辨率 |
